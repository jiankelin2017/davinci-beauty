DaVinci Beauty 美颜插件 —— 交付说明

【当前构建 2026-11-07】1.1.2.1：上一版想把「脖子附近那块跟着人走的白色长方形」修掉，但修反了 —— 这一版先把事情说清楚，再请你看一张图。经过是这样：白块已经用零改动实验切得很干净 —— 把「脖子通道」长度设成 0，白块立刻消失；把磨皮拉到 0，白块还在；关掉整个效果，画面正常。所以它不是磨皮造成的，而是「美白 / 红润」造成的，而这两项只对「蒙版判成皮肤」的像素生效，作用范围就等于蒙版的形状。上一版据此把脖子的左右边界从固定矩形改成「逐行跟随真实皮肤轮廓」，以为能把那两条直边化掉。真机上结果相反：日志 36 条采样显示，脖子那块覆盖的面积从 2.22% 涨到 3.33%（+50%），脸几乎没动，白色方块反而更明显（椭圆档变椭圆、矩形档变方形，说明白的轮廓就是蒙版的轮廓）。原因有两个：① 跟随肤色时左右最多探到 0.70 倍脸宽，而旧矩形只有 0.45 倍 —— 注释写的是「上限」，我理解成「会收窄」，实际它是个放大系数；② 探测规则是「连续 3 个像素不是肤色才停」，当整行都被判成肤色时，它会一路顶到 0.70 这个上限，边界又退回一条直线。所以这一版不再猜：加了一个诊断开关 BEAUTY_DUMP_OUT，指向一个目录之后，插件会把「检出人脸的前 6 帧」的输入图、输出图、蒙版图各存一份（PPM / PGM 格式，零依赖，任何看图软件都能开，三张同尺寸同朝向，可以直接叠着比）。你只要双击根目录的「诊断_导出白块帧.bat」，按提示做三步（播到白块最明显的地方暂停 → 按一下左方向键 → 再按一下右方向键），图就会落在 C:\ProgramData\DaVinciBeauty\dump 里。拿到这三张图，我能直接读出四个数：那块区域在原始画面里是什么颜色（真肤色还是米色衣服）、它对应的蒙版值是满值还是渐变的、被提亮了多少级、以及变化区域的形状填充率（矩形接近 1.00、椭圆约 0.785）。这四个数能把「真皮肤被提亮」和「衣物被误判成皮肤」彻底分开 —— 这两种的修法正好相反：前者要加长边界羽化，后者要把脖子从美白里摘出去。不开这个开关时这段代码一次都不执行，画面与上一版完全一样（强制回旧矩形后逐字节基线 18/18）。

【上一版 2026-11-07】1.1.1.4：这一版不改画面，只把「时间到底花在哪」量清楚 —— 因为上一版收工时那个「插件只占帧预算 9%」的结论有个盲点。那个 9% 是拿「GPU 磨皮 3.77ms ÷ 41.7ms」算的，只统计了磨皮这一段。可日志里一直有 `render #` 那行完整账：真机 1080p 实测「转in 3.0 + 引擎 8.7 + 转out 3.7 ≈ 15ms」，占 24fps 下 41.7ms 预算的 32%~45%。其中「转in」「转out」这 6.7ms 是**格式转换**（Resolve 给的是 32 位浮点画面，引擎只吃 8 位），代码是 AVX2 但**单线程逐行**，跟算法正确性毫无关系，却比磨皮本身还贵 1.7 倍。而磨皮只占引擎那 8.7ms 里的 3.5~4ms，剩下的 4~9ms 此前一分钱数据都没有。所以这一版只加仪表：引擎内部插五对计时点，日志每 30 帧打一条「帧分解 掩码= 磨皮= 色调= 回填= 美形= 合计=」，五个数加起来恒等于合计，可以和 render 行的 sdk= 对账；同时并列打「工人掩码=」—— 人脸检测与画蒙版跑在后台线程上，不在这条时间线里，不打这个数会误判成「蒙版很便宜」。所有计时只读，画面与上一版完全一样（逐字节基线 18/18 未变）。顺带更正一条我自己写错了三版的结论：「GPU 计算只要 0.17ms」量的是 CPU 下发命令花多久，不是 GPU 算完花多久；GPU 真正执行在「等 GPU」里，约 1.4ms。所以磨皮的构成是「CPU 搬 2.3 + GPU 算 1.4」，不是「算 0.17、搬 3.3」—— 方向没变（搬更贵），比例要改。请你重启 Resolve 再播一遍同一段素材，我读「帧分解」就能给出下一步该动哪一段、大概能省多少。

【再上一版 2026-11-07】1.1.1.3：**上一版的猜测被真机数据推翻了，ROI 其实不胖**。你播的那段 1080p 素材收上 37 条诊断：人脸区域占画面中位 32.5%，人脸框本身已占 22.9%，两者相除（倍数）中位只有 **1.4 倍**（范围 1.2~1.6）—— 我上一版猜的是 15~25 倍，错了一个数量级，错在把「人脸区域占整幅画面的比例」当成了「相对人脸框的倍数」。多出来的那 40% 面积基本全是脖子：脖子参数是 0.65 倍脸高，把包围盒高度撑到 1.65 倍脸高，除以人脸框的 1.15 倍正好 1.43，与实测 1.4 对得上；肤色误判这条可以排除（皮肤只占 7.78%，远小于人脸框的 22.9%）。但真正扎眼的数是：**人脸区域里只有 24% 的像素是皮肤**（32.5 ÷ 7.78 = 4.2 倍），剩下四分之三都是「一个矩形把 2~3 张脸之间的空隙一起罩住」的浪费 —— 这靠调参数动不了，只能把一个大矩形拆成每张脸一块。所以本版**只加一个数来判定拆不拆**：日志里「掩码诊断」那行新增「分块」，含义是「按每张脸单独一块算，要搬的像素是现在的几倍」。读法很简单：**分块 ≥ 1.0 就说明拆了白拆；小于 0.9 才值得动管线**。这个数只做统计，画面与上一版完全一样（逐字节基线 18/18 未变）。另外附带把「延迟取回」判死了：这段素材上 7 条稳态采样全部没走成（阻=rect 6 条、noprev 1 条），命中率 0，不再往这条路投钱。后续实测：多脸样本「分块」中位 0.43x 看似值得拆，但每块都要单独付 232 像素的管线边距，3 张脸实算反而多搬 67%~94%，该路线已判死。

【更早一版 2026-11-07】1.1.1.2：只加诊断，不改画面。上一轮已经查清：卡的不是 GPU 计算，是「搬画面」—— 磨皮只算脸那一小块，但每帧要来回搬 10.8MB 数据，比 1080p 整帧还多，GPU 计算只占 0.17ms。所以真正的提速办法是把「人脸区域」缩小。但人脸区域为什么会涨到画面的 74%×88%，上一轮只是猜，没量过。按上次事故的教训（一个没验证的假设直接导致真机出错），这一版**先把数拿到手**：日志里新增一条「掩码诊断」，每 12 帧一条，给出三个数 ——①「盒」人脸区域的包围盒占画面比例；②「脸盒」人脸框本身占画面比例，两者相除得到「倍数」：倍数接近 1 说明脸框本身就大，远大于 1 说明是脸框之外的皮肤在把区域拉大；③「脖」= 面具里由脖子通道新增的比例，占一半以上就说明脖子是主因。这三个数只做统计、**完全不参与画面计算**，所以画面与此前一模一样（逐字节基线 18/18 未变）。

【历史 2026-11-07】1.1.1.1：定版收尾。1.1.1.0 真机连续播放验收通过，「以脸为中心的长方形遮罩」彻底消失，画面正确。本版只做三件事：① 日志采样从每 10 帧恢复为每 60 帧（诊断结束，不再刷屏）；② 首次产出正式一键安装包（v1.1.1.1）；③ 定版归档。真机实测：连续播放时 GPU 磨皮合计中位 3.5ms、p90 4.8ms、峰值 11~13ms（只在起播/跳转那一帧），帧预算 41ms，**稳态无掉帧**，画面无异常。「延迟取回」这条优化在你这段素材上基本用不上（日志里大多数行是「阻=rect」，因为人脸在镜头里大幅移动，框一直在变）—— 但它退得对，画面正确才是硬指标。下一个方向已定为「ROI 瘦身」：真正的瓶颈是 ROI 太大（常见 1400×950，占画面 74%×88%），单帧要搬往返 10.8MB，比 1080p 整帧还多，而 GPU 计算只要 0.17ms。

【历史 2026-11-07】1.1.1.0：给「延迟取回」补上静止判据。1.1.0.0 为了提速，让第 N 帧只提交、第 N+1 帧才取回上一帧的结果，但它只检查「参数没变」，没检查「画面本身也没变」，于是把上一帧那一整块贴到了本帧上，画面出现以人脸为中心的大长方形、边界清楚、闪烁、像放大。1.1.1.0 补上两条硬前提：① 人脸框（ROI 矩形）必须完全一致；② 矩形内的画面必须被判定为静止（按 8 像素网格采 2.1 万个点，同时比 RGB 与蒙版，平均差 <=1.5 且「差超过 8 的点」占比 <=0.5%）；任一不满足就当场算完再取，宁可慢一帧也不出错。日志行末新增「阻=」字段：ok 走成了 / noprev 没有上一帧 / jump 跳帧或超时 / param 参数变了 / rect 人脸框变了 / motion 框内画面在动。台架判据也彻底重写：旧版拿「这条流水线会拼出什么」当期望值，等于自己给自己出题，7 行全过却验的是错设计；现在三种情况一律跟 CPU 结果逐字节比，21 帧全 0 差异。想彻底关掉：beauty.ini 里写 gpu_smooth_pipeline = off。

【历史 2026-11-07，画面有误勿用】1.1.0.0：实施 2c 延迟取回 —— GPU 磨皮不再每帧等 GPU 算完才取回，改成「第 N 帧取回第 N-1 帧早已备好的结果，再上传本帧、算完只提交拷贝就返回」的一帧流水。依据：1.0.10.2 的 40 样本实测，18% 的帧超预算 6~14ms，超出的部分全卡在两个 GPU 同步点上，CPU 侧三项（拷/补齐/算）纹丝不动。做法：pack 三张 DYNAMIC 与 stage 各做成两份轮流用（只做一半没用，写侧和读侧会互相转嫁积压）；texSrc/平面/texDst 仍单份。**代价是 ROI 内画面晚一帧**（ROI 外仍是本帧 src）——台架把这个代价量出来了：1080p、每帧左移 3px 的序列上，「上一帧结果」与「本帧结果」相差 602 万字节、maxdiff 255（整块 ROI 全不同），只是磨皮是低频变化，23.976fps 下肉眼分辨不出。**三条前提缺一就自动退回同步**：同一实例、帧号连续、两次调用间隔 ≤150ms —— 所以静止画面、拖动播放头停下那一刻、首帧都还是迟零帧。新增配置项 gpu_smooth_pipeline：默认 auto；做慢动作或单帧精修怕这一帧差异时改成 off，立刻回到每帧同步。验证：台架新增第 4 组判据 pipelineCase（期望 = 本帧 src + 上一帧矩形内取上一帧 CPU 结果），7 行全 0 差异，逐字节基线仍 18/18，台架静态 5/5 + 运动 6 帧全过。按四段式判定，这次加了新配置项与新渲染路径，走功能位。上一版 1.0.10.2：诊断期临时加密采样，只改一个取模常量（构建位 +1）—— GPU 磨皮那行日志的周期从每 60 帧改成每 10 帧，ini 注释同步。算法、默认值、画面未动。原因：1.0.10.1 只攒到 3 个热状态样本，判断不了「等 GPU 尖峰」（0.76→5.19）的出现频率，也验证不了区间均值 4.40→4.78→5.28 递增是真热节流还是噪声。定位结束后会改回 60（每行日志有写文件开销）。**加密后的 40 个样本推翻了上一版的两条结论**：①Map 不是恒 0.02ms——19% 的帧在 2~14.56ms 之间；②首帧慢不必用「冷启动伪影」解释，与稳态是同一种阻塞（GPU 有积压 Map 就等）。**最有价值的发现是责任划分**：36 个有效样本按整帧间隔分成「按时帧 25 个（中位 41ms，正好是 23.976fps 的预算）」与「掉帧 11 个（中位 53ms）」，两拨相比 CPU 侧三项几乎不动（拷 0.90→0.99、补齐 0.72→0.70、算 0.15→0.18），多出的 6~14ms 全部落在两个 GPU 同步点上（写侧 Map 0.02→3.60、最大 14.56；读侧等 GPU 1.23→3.48、最大 9.42）。也就是说约 18% 的帧超预算，原因不是算得慢，是 GPU 没算完就被同步等住了。**因此 2c 双缓冲从「放弃」改回「待实施」**，而且读写两侧必须同时双份——只延迟读侧会把积压转嫁到下一帧开头的写侧 Map（实测写侧比读侧更凶）。同时「区间均值递增＝热节流」的猜测也作废：380 帧的均合计在 5.0~5.5 之间横摆，后 100 帧反而回落到 5.03~5.18。1.0.10.1：纯观测版，只加两个日志字段、不改逻辑。起因是 1.0.10.0 的真机日志给出一个对不上的数：1920×1080 工程「上传=2.90ms」，而实际写入只有 2.33 MB，折合约 800 MB/s —— 纯 memcpy 不可能这么慢，所以怀疑大头是 Map(WRITE_DISCARD) 在等 GPU 让出上一帧那张 DYNAMIC 纹理。当时（仅 3 个样本）判为「Map 恒 0.02ms、首帧慢是冷启动伪影」，**这两条已在上一段被 40 样本修正**。逐帧验算另确认四项之和与合计完全闭合（最大偏差 0.01ms），没有隐藏开销——这一条仍然成立。另记一条测量口径：分项耗时必须用连续播放的多个样本比较，首帧行含着色器编译等一次性开销；**样本少于 10 个也不能下「恒定/不存在」这类结论**，本轮就是 3 个样本全落在好帧上，把一条真实路径整个否掉了。1.0.10.0：修 1.0.9.0 的一个实装缺陷 —— 承诺的「初始化日志打出适配器型号」在生产路径从未生效（播报所在的 gpuSmoothInit 在插件本体无人调用，走的是内部懒加载），本版把播报移到懒加载处并保证只打一次；只改日志与注释，算法、默认值、画面未动（18/18 逐字节一致）。**1.0.10.0 已真机验证通过**：日志出现「GPU 磨皮后端已就绪：NVIDIA GeForce RTX 5060 Laptop GPU [厂商 0x10DE，显存 7.7 GB]」。1.0.9.0：gpu_smooth
