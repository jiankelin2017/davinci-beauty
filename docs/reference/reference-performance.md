# DaVinci Beauty 性能：结论与实测账

> 适用代码版本：1.3.6.0 ｜ 状态：Active ｜ 最后更新：2026-11-08 ｜ 维护人：Jian ｜ 替代文档：原 `01_ofx插件源码/性能方案.md`

**这份文档管**：一帧的时间花在哪、已经拿掉了多少、哪些优化被证伪、下次动手前该先量什么。
**不在这里管**：架构约束看 `reference-architecture.md`，逐版本变更看 `docs/CHANGELOG.md`，验收流程看 `docs/guides/guide-acceptance.md`。

> **口径先声明**（不声明就会读出矛盾数字）：下面所有毫秒数分两种口径，混用没有意义。
> **口径 A（真机稳态）**：`ofx.log` 里的 `帧分解` 行，掩码按 `kMaskEverySync` 节流（4 帧一次），代表用户实际感受到的速度。
> **口径 B（每帧全算）**：`NamaSelfTest` 离线连跑，掩码每帧都算，另含约 35 ms 的文件 I/O 噪声，只用于同版本 A/B 对比，不代表用户体感。
> 同一帧两种口径能差 2 倍以上，历史上多次因此误判"优化没生效"。

## 0. 摘要

**一句话**：1.2.5 → 1.3.4 期间口径 B 从 ~24 ms 降到 ~14 ms（−42%），全部改动**逐字节不变**；1.3.5.0 只修失败路径、1.3.6.0 只修色调段的数据竞争，**两版的耗时口径都没变**。

只需要记住五条，其余按需查：

| # | 结论 | 详见 |
|---|---|---|
| 1 | 掩码那 10 ms 里 **6.75 ms 是 ONNX 检测**，绘制只占 2~3 ms —— 改绘制再多也只动零头 | §2.1 |
| 2 | 这条线上唯一的大收益是**检测复用**（1.2.9）：掩码 9.8 → 4.7 ms，代价是边界滞后约 1 帧 | §2.2 |
| 3 | GPU 磨皮 4.5 ms 是**GPU 真在算**，不是 dispatch 排队 —— BOX2D 合并实测证伪 | §3.2 |
| 4 | 首帧 173~235 ms 是**预热**（着色器编译 + 纹理落实物理页），不是稳态问题；1.3.4 已挪到 `createInstance` | §3.4 |
| 5 | 性能改动一律以**逐字节不变**为硬约束，靠 18 条基线 + 5 张 mask md5 守；要改像素就得重标基线并写明代价 | §5 |

## 2. 掩码这条线（最大单块）

### 2.1 打点结果：检测吃掉 2/3

`BEAUTY_MASK_PROFILE=1`（默认零开销），1080p 真机帧：

```
掩码分解 检测=6.75 memset=0.14 肤色=0.18 脸框+脖=2.67 保护=0.00 合计=9.73
```

**这一行终结了此前所有的猜测**。在拿到它之前，团队按"绘制是大头"的思路连做了两个版本，只动了 2~3 ms。下表是几个单独实验，**来自不同时点、不能相加**，只用于说明"每项各值多少"：

| 关掉什么 / 改什么 | 掩码 | 说明 |
|---|---|---|
| 默认 | 11.15 ms | 1.2.7 时点 |
| 脖子带关（`BEAUTY_NECK_LEN=0`） | 9.69 ms | 脖子带只占 1.5 |
| 推理线程 2 → 8 | 11.85 → 9.84 | 检测约 2 ms |
| 绘制并行前后 | 13.9 → 11.1 | 绘制约 2~3 |
| `memset` 两张全帧缓冲 | **0.14 ms** | "4 MB memset 很贵"的猜测是错的 |

几项加起来只解释了 ~5 ms，其余 ~7 ms 当时被归为"固定开销"。打点后才发现：那 7 ms 里 **6.75 是 ONNX 检测**（表中"推理线程"那 2 ms 是检测内部并行的收益，属同一笔账，不另计）。

**教训**：优化前先在函数内部打点，不要靠推理切分。这条是本轮最大的成本。

### 2.2 检测复用（1.2.9，已落地）

判据：64×36 灰度缩略图的平均绝对差 ≤ `g_detThr`（默认 2.0）且距上次真检测不超过 `g_detAge`（默认 4 次）时，沿用上一帧人脸框。回退开关 `BEAUTY_DET_REUSE=0`。

24fps 连续 11 帧实测（1080p）：

| | 复用帧（8/11） | 重测帧（3/11） | 平均 |
|---|---|---|---|
| 检测 | **0.03 ms** | 6.5~7.7 ms | 1.9 ms |
| 掩码合计 | 2.7~2.9 ms | 9.4~10.5 ms | **4.7 ms** |

掩码平均 9.8 → 4.7 ms（**−52%**）。

质量代价（同序列，复用 vs 全检测的掩码逐字节比，`mean|Δ|/255`）：`0.000 / 0.300 / 0.000 / 0.179 / 0.260 / 0.000`，差异集中在羽化带，≤1% 像素差 >8 级。即**边界滞后约 1 帧**；静止与慢速镜头零差异，快甩头由 `detAge=4` 兜底重测。

> **单帧用例测不到这条优化**：18 条基线和 5 张参考帧都走"首帧必检测"，所以逐字节不变，效果只能在**序列**上量到。这是它最容易被误判为"没生效"的原因。

### 2.3 次要项：绘制并行与推理线程

- **1.2.7 绘制并行**：`buildMaskInto` 的脸框矩形/椭圆两支按行并行（走持久池 `parallelRows`），统计量 `px`/包围盒改成"每块局部累加 + 末尾合并"。同步路径掩码 13.9 → 11.1 ms。**脖子带必须保持串行**——它读的 `colEnd` 是 `thread_local` 的，换线程会读到空表。
- **1.2.7 推理线程可调**：`BEAUTY_INFER_THREADS`（1..16，默认 2）。实测 2/4/8 线程掩码 11.85/10.53/9.84 ms。**导出前设 6~8 是纯赚，直播别开**——直播场景编码要占 4~6 核。

### 2.4 压不下去了

掩码剩余 4.7 ms 里，重测帧仍是 9~10 ms。继续降只有两条路，都不划算：

| 手段 | 预期 | 代价 |
|---|---|---|
| 检测输入边长 640 → 480 | 检测 ×0.6 | 侧脸/小脸召回下降，需真机核 |
| 掩码降分辨率（1/2 算再上采样） | 13 → 3 | 边界会糊。1.1.3~1.1.7 九个版本都在治边界，**不要动** |

## 3. GPU 磨皮这条线

### 3.1 执行 4.53 / 拷贝 0.11

`BEAUTY_GPU_PROFILE=1` 时每帧一行（`D3D11_QUERY_EVENT`）：

```
GPU 提交分解 执行=4.53 拷贝+回读=0.11
```

| 假设 | 实测 | 判定 |
|---|---|---|
| 提交 / Flush 慢 | 算 = 0.50 ms（含 Flush） | ✗ |
| staging 拷贝大（4.5 MB BGRA） | 拷贝 + 回读 = 0.11 ms | ✗ |
| dispatch 链执行慢 | **执行 = 4.53 ms** | ✓ |

10 次 dispatch（DOWN → BOXH/BOXV×3 → AMP → BOXH/BOXV×3 → COMPOSE）跑在 512×540 平面上只有 ~2.8M 像素操作，4.53 ms 说明瓶颈是**每像素的工作量**，不是像素量也不是排队。

### 3.2 BOX2D 合并：假设被证伪

按"dispatch 次数是瓶颈"的推断，实现了 `CSBox2D`（32×32 一个 group，groupshared 存 44×32 的 H 结果，V 用滑动窗），`BEAUTY_GPU_BOX2D=1` 开关，默认关。

| 版本 | 执行 | A/B 输出 |
|---|---|---|
| 每线程 4 行、每点 13 tap | **5.97 ms**（旧路径 4.46） | mean Δ=0.000，max 2 级，3 px |
| 改滑动窗（每点 +2 次 shared 读） | **5.65 ms**（旧路径 5.89） | mean Δ=0.000，max 3 级，1 px |

两点结论：

1. **数值是对的** —— 两版都与两次 dispatch 的结果一致（最大差 2~3 级、个位数像素），flush 语义对齐没问题；
2. **性能无收益** —— 6 次 dispatch 合成 3 次，执行时间不变。所以"4.53 ms 是 dispatch 开销"这个推断**是错的**。

真实成本是 **tap 数 × 像素数 × 趟数**：512×540 × 13 taps × 3 趟 × 3 通道 ≈ 3200 万次乘加。GPU 在老老实实算。

> 同一张表的"旧路径"出现了 4.46 与 5.89 两个值，是跨次测量的波动，说明这条通路的单次测量噪声在 ±25% 量级。**只有同一次构建里的 A/B 才可比**。

### 3.3 延迟取回：只在静止时生效

`gpu_smooth_pipeline=auto` 把读回推迟一帧（pack/staging 双份），消掉约 18% 帧的 6~14 ms 卡顿。但判据要求"输出矩形一帧内不变"（`stillOk`），跳舞镜头基本不会命中。

试过用"ROI 向外对齐到 32 的倍数"让矩形恒定：真机 327 帧里 109 帧因包围盒抖 1~3 px 退回同步（白等 4~5 ms）。对齐后矩形确实稳定了，但**14/18 基线会变**（半分辨率平面的采样相位跟着 ROI 起点走），**已回退**。要做这条，得先把平面原点的相位固定成与 ROI 无关，属于 GPU 路径内部改动。

### 3.4 首帧预热前移（1.3.4，已完成）

D3D11 设备 + 着色器编译 + 全局纹理原先是第一次 render 时懒加载，真机首帧磨皮 173~235 ms（稳态 4~5 ms），起播和导出片头会顿一下。

现在 `createInstance` 里跟着引擎预热一起调 `gpuSmoothInit()`，耗时 >5 ms 才打一行日志。失败不影响正确性——首帧仍会重试（原懒加载路径保留）。

真机验证：`ofx.log` 里出现 `createInstance 预热 GPU 成功 耗时=...`，且 `帧分解` 的第一帧 `磨皮=` 从 173~235 掉到 10 ms 量级。

### 3.5 再往下只能拿画质换

| 手段 | 预期 | 代价 |
|---|---|---|
| 趟数 3 → 2（盒式³ → 盒式²） | −33% | 模糊核形状变了，观感偏"方" |
| 半径不变、平面降到 1/3 分辨率 | −55% | 细节丢失，边界更糊 |
| 可分离高斯近似（一次 H、一次 V，核更宽） | −50% | 与参考实现不再逐像素对齐 |

**这条线到此为止。** GPU 已经是"算得动但在真算"，再往下都是拿画质换时间，而画质正是前面九个版本在救的东西。

## 4. 其他段落

### 4.1 色调权重低通并行（1.3.1，已完成）

`toneColor` 里那两遍盒式均值（R=24 长斜坡 + R=3 门控）原本串行，占色调段 4.1 ms 的一半以上。现在 H 遍按行切、V 遍按列切，走 `parallelRows`。

> **关于当时的收益数字（−3.8 ms），账是对不上的**：色调段总共 4.1 ms，"占一半以上"意味着可省上限约 2 ms，而报出的整帧 wall 降幅是 3.8 ms，且该 wall 含约 35 ms I/O 噪声。**这 3.8 只能当"有改善"，不能当幅度引用**，也是 §1 表格里色调格留空的原因。要拿到真实收益，需在 `toneColor` 内部按 H/V 两段分别打点重测。

**踩到的坑（已写进代码注释）**：`wbuf/wtmp` 是 `thread_local`。并行前必须在**调用线程**取好裸指针再传进去，否则工作线程拿到各自那份**未 resize** 的 vector，写越界直接 `0xC0000005`。第一版就是这么崩的。

### 4.2 回填

已并行（≤8，Resolve 里 11），2.3~3.1 ms，未优化。

## 5. 怎么量

### 5.1 三个开关

| 开关 | 输出 | 用途 |
|---|---|---|
| `BEAUTY_MASK_PROFILE=1` | `掩码分解 检测=… memset=… 肤色=… 脸框+脖=… 保护=…` | 掩码内部切分，默认零开销 |
| `BEAUTY_GPU_PROFILE=1` | `GPU 提交分解 执行=… 拷贝+回读=…` | 区分"算得慢"和"等得慢" |
| 真机 `ofx.log` 的 `帧分解` 行 | 每段耗时 | 口径 A 的唯一来源 |

### 5.2 多核利用率

`NamaSelfTest` 同一帧连跑 6 次，比 **wall 与进程 CPU 时间**。下表是 1.2.5 时点的数据，**只用来演示算法**（wall 含自测路径 I/O，不要与 §1 的分段值对比）：

| 调用 | wall | CPU | CPU/wall |
|---|---|---|---|
| 1 | 66 ms | 94 ms | 1.4 |
| 2 | 59 ms | 172 ms | 2.9 |
| 3 | 58 ms | 188 ms | **3.2** |
| 4 | 59 ms | 94 ms | 1.6 |

20 核机器峰值 3.2 核——当时根因就是 §2.1 里那个"掩码整段单线程"。前两次偏低是线程池冷启动，**至少跑 6 次取后段**，否则会误判"没并行"。

### 5.3 硬约束：逐字节不变

任何性能改动都必须过这两关，否则视为改变画面：

```bat
python 04_验收工具/baseline.py check     :: 18 用例逐字节
```

掩码相关改动另比 5 张参考帧的 mask md5（1.2.7 起未变）：

```
ref_g_005   148f4dab662018f74faae41dfdcbb46f
ref_g_010   87d0db73ca783f285d3265dd2932d1b3
ref_g_015   e2b1f10b088e5ebb9935e661aa00058a
ref_g_020   19a85c9dfb647c24e684ae3e3525b531
ref_resolve ad330857b4079d4510f2d18ed7dd6b7e
```

确实要改像素时（如未来做高斯近似），必须**逐用例核 ±1 级并重标基线**，且在 `CHANGELOG.md` 写明降级点——不允许"顺手改了没说"。

### 5.4 回归偶发失配：已定位为数据竞争（1.3.6.0 修复）

**一句话**：不是测量噪声，是 `toneColor()` 里的数据竞争。2026-11-08 定位、修复，基线已重标。

**机制**：`beauty_freq.cpp` 的 `toneColor()` 用 `runRows` 按行并行写 `dst`，而同一个循环里为边缘门控做 Sobel 时读的是 `dst` 自身的上下左右邻域。块边界那两行读到的邻域究竟是「已美白」还是「未美白」，取决于哪个线程先跑完 → `mag` 变 → `edge` 变 → `sk` 变 → 输出差 1 级。这是 C++ 未定义行为，不只是数值抖动。

**证据（全部实测）**

| 实验 | 结果 |
|---|---|
| `blur62_wh100` 单跑 2100 次 | 33 次输出不同（1.57%） |
| 异常像素的行坐标 | 全部是 `261 + 35k`（261/296/331/366/401/471/506）及 `y±1`；35 = 行块高（ROI 高 280、8 块） |
| 强制 CPU 各 300 次：`blur00` / `blur62` / `blur62_wh100` / `cl50` | `0` / `0` / `6` / `4` —— 只磨皮不抖，加美白就抖 |
| 强制 CPU 400 次 vs 强制 GPU 800 次 | 3 次 vs 4 次，两边都抖 |
| `BEAUTY_INFER_THREADS=1/2/4` 各 200 次 | 异常率都是 0.5%，**与推理线程数无关** |
| 修复后 `blur62_wh100` / `cl50` 各 1200 次 | 单一 md5，0 次异常 |

**三条作废的旧归因**（都写进过文档，现在都不成立）：①「GPU 争用下的设备创建退让」——强制 CPU 一样抖；②「与推理线程数相关」——三个线程数异常率相同，早期「单线程 36/36 全绿」是采样不足（真实率 1.5%，36 次期望 0.54 次）；③「需要并发才触发」——单跑 2100 次照样抖。

**修法**：把 Sobel 挪到写回之前单独跑一遍，结果存 ROI 大小的 `ebuf`（1 字节/像素），写回循环只查表。顺带省掉写回时的九宫格重算。

**耗时**：量不到可分辨的差异。同一进程内循环 80 帧、新旧 DLL 交替 3 轮，单帧中位差 `−0.46 ms`（`wh100`）与 `−0.79 ms`（`cl50`），但单轮差值在 `−2.4 ~ +2.3 ms` 之间变号——噪声远大于效应。结构上是「多一次 ROI 只读遍历（+5 B/px）」换「写回循环少 9 次邻域读取」，方向相反，量级都在 0.1 ms 级。

**代价**：画面会变，且不止竞争那几行。旧代码在同一行块内处理第 y 行时，`y-1` 已被本线程写过、`y+1` 还没写，门控算的是混合值；改成统一读进入函数时的状态（美白前），才与磨皮侧 `sobelEdge(src,…)` 对齐。

| 用例 | 变化 |
|---|---|
| `blur62_wh100` | 1458 像素（0.22%），最大 3 级 |
| `blur62_wh30` | 192 像素，1 级 |
| `cl50` | 700 像素，1 级 |

差异全部落在脸部 ROI 内，18 个基线 md5 里有 14 个（全部 `whiten>0`）随之更新。`baseline.py update` 现在**一次通过**，不再需要 `BEAUTY_INFER_THREADS=1` 那个绕法。

**没修的地方**：`clarityRgb()` 同样并行写 `dst`，但只读自己那一像素，不构成竞争（逐处核对过）。

## 附：两条与性能无关、但曾记在这里的记录

已迁出正文，避免性能文档被工程排障淹没：

- **构建可复现**：`build.ps1` 的 `Reset-PeTimestamp` 清零 COFF 与 `IMAGE_DEBUG_DIRECTORY` 两个 `TimeDateStamp`，同源码重编 md5 恒定（`5655699…`）。`/Brepro` 在本工具链**不生效**。详见 `reference-architecture.md` §3。
- **PowerShell 5.1 编码坑**：`build.ps1` 若含非 ASCII 注释，以 GBK 解码时行尾 CRLF 会被吃掉，**下一行的数组元素被当成注释内容**（曾因此吞掉 `/Brepro` 和 `$sandboxDefine`，表现为"宏没到编译器"）。修法是脚本保持纯 ASCII。沙箱构建的结论见 `docs/guides/guide-package.md`。
