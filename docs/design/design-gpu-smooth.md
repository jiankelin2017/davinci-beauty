### 两个必须记住的坑

1. **`runBox` 已经是一整趟（H+V），循环里再调两次 = 跑成 2×passes 趟。**
   第一版就是这么写的，passes=3 变成 6 趟，模糊半径直接翻倍，
   画面差 9~14 灰阶。是离线台架一次对出来的 —— 这类错在 Resolve 里
   只会表现为「效果好像变强了」，根本定位不到。

2. **`surface3RgbBand` 的 `roi` 参数根本没被使用。**
   函数体里只有 `if (... || roi.empty()) return;` 这一处引用，
   之后全部按 `w, h` 全帧算。所以：
   - 之前文档里「磨皮已 ROI 化」的结论是**错的**；
   - 4K 的 71.5ms 是**全帧**工作量，脸外像素白算；
   - 这对 CPU 路径是一个尚未兑现的大优化（离线估算 4~6×），
     与 GPU 无关，随时可独立做。

### ★ ROI 外扩不是「够用就行」，有一步算错了会稳定差 1~2 灰阶

**1.0.1.1 曾把剩余 2~3 字节差异判为「1 ULP 翻越 .5 取整边界、驱动 ISA 选择不可控」。
这个判断是错的。** 真正原因是 ROI 外扩量少了 `passes × 32`。

#### 硬约束

```cpp
// gpu_smooth.cpp
const int growP = passes * 32 + passes * (r2 + ra) + 2;
//               ↑ 新增项        ↑ 模糊传播        ↑ 双线性
```

#### 为什么 `passes × 32` 是硬需求

`bandBoxH` / `bandBoxV` 每 32 像素用「从头重算窗口和」的方式纠正 float 累加误差
（`kFlush = 32`）。这带来一个副作用：

- ROI 最外一块（局部 x = 0）重算窗口时，左边**没有数据**，只能 clamp 到自身；
- 整帧版同一个像素重算时，左边读到的是**真实邻居**；
- 于是 ROI 最外一块**整块**的窗口和与整帧不同；
- 下一块重算要读左邻 r 个像素 → 污染向内容方向传染**一块**；
- 一共传染 `passes` 次 → 污染半径 = `32 × passes`。

#### 实测证据链

ROI 内缩扫描（`[SCAN]`，1080p 横，单位：字节差异数）：

```
inset  32:12038   44:7723   64:1613   96:0   128:0   160:0
                                    ↑ 归零，恰等于 32 × passes(3) = 96
```

修复前 `growP = passes*(r2+ra)+2 = 20`，连一个 32 周期都不够。

#### 排除法（全部实测 0 位差，用于证明「不是别的原因」）

| 对照项 | 结果 | 排除了什么 |
|---|---|---|
| `C 平面`（下采样） | 0 位差 / 106400 点 | 上传、下采样、坐标映射 |
| `gpu vs refG` / `gpu vs refP` / `refG vs refP` | 全 0 位差 | GPU 算式与两路算法复刻 |
| `cpuBox(direct) vs prod` | 0 位差 / 494656 点 | CPU 生产结果可被直接复现 |
| `cpuBox t=1 vs t=12` | 0 位差 | 并行无竞态 |
| `passes=1/2/3 refP vs cpuBox` | 全 0 位差 | 单趟与多趟结构 |
| `cpuBox(crop) vs refP` | 0 位差 | 裁剪输入的 box 段同构 |

排到最后只剩「ROI 与整帧的边界」这一项，扫描一测即中。

#### 顺带纠正一个台架方法学错误

台架里原来有一项「裁剪对拍」：把 GPU 实际处理的矩形裁出来交给 CPU 再跑一遍，
用来区分「算法错」与「halo 不足」。**这项判据从设计上就不成立**：

`bandBoxW` 的半径是「画面宽度 × 比例」算出来的：

```cpp
int k = (int)(frac * ww + 0.5f);   // ww 是半分辨率宽度，图裁小了它跟着变小
if (k < minW) k = minW;
if ((k & 1) == 0) k++;             // 半径必须是奇数宽
```

所以裁剪之后算出的 r 可能与全帧不同 —— 裁剪版 CPU 跑的是**另一组参数**。
实测四个画幅完全吻合这个解释：

| 画幅 | 全帧 r1/r2/ra | 裁剪后 r1/r2/ra | 裁剪对拍 |
|---|---|---|---|
| 1920×1080 | 2/4/2 | **1/2/1** | 有差异 |
| 3840×2160 | 5/9/5 | **2/4/2** | 有差异 |
| 1080×1920 | 1/2/1 | 1/2/1（恰好相同） | **0** |
| 640×394 | 1/2/1 | 1/2/1（本来就是全图） | **0** |

「裁剪对拍 = 0」的两个画幅，恰好是半径没变的两个。现在该项已在台架里
标注为**参考项，不计入判定**，并在日志里同时打印两边实际 r 值。

## 2. 生产默认路径拆解

面板默认 `blurType=0`（双边）→ `g_cfg.s3Band=1` → `surface3RgbBand`，
`beauty_smooth.cpp:1087`，173 行，**四个阶段**：

```
src (RGBA8 全帧)
  │
  ├─ Stage 0  下采样 2×2 盒式 → 3 个 float 平面 (ww×wh)，值域 0..255
  │            ww,wh = ceil(w/2), ceil(h/2)；不足 8 像素则保持原分辨率
  │
  ├─ Stage 1  B1 = bandBoxN(src, r1, nPass)     ← 窄模糊，可分离 H+V
  ├─ Stage 2  B2 = bandBoxN(src, r2, nPass)     ← 宽模糊，r2 保证 > r1
  ├─ Stage 3  amp = bandBoxN(|C.g − B2.g|, ra)  ← 只测绿通道
  │
  └─ Stage 4  上采样回全分辨率 + 逐像素合成：
              surfaceKeep 软膝 + 振幅门控 + I/e + skin 混 + 眼保护 → dst (RGBA8)
```

半径全部由 `bandBoxW(ww, factor, minR)` 现算，与分辨率绑定 —— 这点很重要：
**GPU 侧必须调同一个函数求半径**，不能在 shader 里另算，否则两边核不一样。

### 关键性质

- 四个阶段**全是局部算子**，无跨像素依赖（盒式模糊虽然看起来有邻域，但已经拆成 H/V 两趟）
- 中间数据是 float 平面，尺寸只有全帧的 **1/4**（半分辨率）
- 合成阶段需要 `mask`（掩码）和 `protect`（五官保护）两张全分辨率 8bit 图

## 3. GPU 映射方案

每阶段一个 CS，共 5 个 kernel（Stage 1/2/3 共用同一个 box shader，靠参数区分）：

| kernel | 输入 | 输出 | 说明 |
|---|---|---|---|
| `downsample2x2` | RGBA8 SRV | 3 × `RWTexture2D<float>`（或 1 张 `float4`） | 2×2 平均，边界 clamp |
| `boxH` | float | float（临时） | 滑动窗口，每行独立 |
| `boxV` | float | float（临时） | 同 `boxH`，转置 dispatch |
| `amplitude` | C.g, B2.g | float | `abs()` 后立刻接 boxH/V |
| `composite` | C, B1, B2, amp, mask, protect | RGBA8 UAV | 逐像素，含 `surfaceKeep` |

**纹理池**：ROI 尺寸 × 1/4 的 float 平面，每平面 4 字节/像素。
4K 人脸 ROI 按 1280×1440 估，半分辨率 640×720 = 46 万像素，单平面 1.8MB，
同时活着约 10 个平面 = 18MB。RTX 5060 有 7.9GB，毫无压力。

**为什么不做全帧**：`gpu_beauty.h` 已实测 4K 全帧搬运 70.7ms，与 CPU 持平，
全无收益。ROI 搬运只要 3.60ms（RGBA8 口径）。所以管线必须沿用现有的 ROI 通道。

## 5. 精度标准：已按 A 执行，已达成

**结论先说：用户拍板 A（严格逐字节、0 字节差异、不许改基线），已达成 —— 4/4 画幅全 0 字节。**

从技术上说，A 之所以能成立，是因为盒式模糊是 `Σ(整数) / n`，输入是 0..255 的整数，
float 累加在 2^24 以内精确无误差；IEEE754 的除法是确定性的。剩下的风险只有两处，
现在都已处理：

| 风险 | 处理方式 | 状态 |
|---|---|---|
| 编译器把 `a*b + c` 融合成 FMA，CPU 与 GPU 融合方式不同 | 所有合成表达式加 `precise`，禁用 FMA/mad 收缩 | 已做，实测 0 位差 |
| `div` 展开后与 CPU `divss` 在极少数分母上差 1 ULP | 1.0.4.0 用 `mad` 残差 + 两次 Newton 精化对齐 CPU | 已修，见第 11 节 |

验收口径：现有 18 条 md5 基线**一条都不需要改**。

## 7. 风险与回滚

| 风险 | 应对 |
|---|---|
| 画面出现细纹/色带 | 默认 off，`beauty.ini` 一行切回 CPU；CPU 路径代码完全不动 |
| 显存不足（低端 GPU） | 纹理按 ROI 分配，失败即回落 CPU，不重试 |
| 半边脸/边缘接缝 | **ROI 外扩必须 = `passes×32 + passes×(r2+ra) + 2`**，少 `passes×32` 会稳定差 1~2 灰阶（见第 0 节）；合成段读 mask 时越界要 clamp |
| Optimus 同步卡顿 | 沿用 P1 结论：管道里不插任何显式 fence，只留 `Map(READ)` 一次自然阻塞 |

## 7.1 交给 CPU 路径的同一课

上面那条 `passes × 32` 的约束**对 CPU 的 ROI 化改造同样成立**，
而且代价更直白：`surface3RgbBand` 现在虽然收了 `roi` 参数却全帧计算
（等于 `roi` 覆盖全图，天然没有边界问题）。一旦真的把 CPU 也 ROI 化，
同样必须按 `passes×32` 外扩，否则同一个画幅的 ROI 版与全帧版会差 1~2 灰阶 ——
而这次的 18 条 md5 基线正是拿全帧版建立的。

## 10. 1.0.3.0 补充施工记录（2026-11-06）

### (1) 资源分配的最终形态

```
逻辑尺寸（cbuffer / dispatch / clamp / 读回矩形）
   imgRW, imgRH, pw, ph        ← 每帧由 bbox 推出，可以逐帧变化
分配尺寸（CreateTexture2D / CopyResource / RowPitch）
   aImgW = (imgRW/64 + 1)*64   ← 始终多留一档，抗桶边界抖动
   aPw   = (pw/64   + 1)*64
   判重：fits = 现有纹理 >= 请求 && 不超过请求 2 倍
```

坑位记录（都是台架逼出来的，别走回头路）：

- **只用标准 ceil 不够**：640 正好整除 64，余量为 0，抖到 641 就跨桶；
  来回抖等于每帧重建。所以是 `(v/64 + 1)*64`。
- **只做「桶相等才复用」不够**：640×394 与 644×398 两个实例交替时，
  20 轮 40 次调用重建 39 次。必须改成容量式复用（`>=`）。
- **不能无限复用大纹理**：4K 切回小图后每帧仍会 `CopyResource` 整张 4K，
  所以加「超过需求 2 倍就收缩一次」。
- `gpuSmoothDebugPlane()` 的 staging 必须用**桶尺寸**（`CopyResource` 要求尺寸一致），
  但只把左上角真实 `pw×ph` 拷给调用方，桶外填充像素不算逻辑数据。

### (2) 去掉 TDR 禁用

`createDevice()` 的 `D3D11CreateDevice` flags 改为 `0`。原先传
`D3D11_CREATE_DEVICE_DISABLE_GPU_TIMEOUT` 会关掉 GPU 超时重置，而 Resolve 与本插件
共用同一块 GPU。这是「插件不该改变宿主策略」的原则问题，与是否真的导致 06:15 闪退无关；
同时删掉「失败后去掉该 flag 重试」的兜底（首选已不带 flag，兜底没有意义）。

### (3) 台架新增用例与判据

`_p2bench/gpu_smooth_test.cpp` 新增 `churnCheck()` / `multiInstanceCheck()`，
以及 `gpuSmooth.h` 的 `gpuSmoothResourceStats()`（重建次数、设备创建次数、当前桶尺寸）。

| 用例 | 硬判据 |
|---|---|
| ROI 逐帧抖动 400 帧 | `rejects=0`、`diff=0`、`deviceCreate=0`、`rebuild<=2`、`reuse==sizeChanges` |

### (4) 已解决：compose 门控段的 1 灰阶残留（1.0.4.0）

1.0.3.0 阶段的证据链（平面全 0 差异 → 在 compose；禁 HLSL 优化 / `/fp:strict`
/ protect=0 均不变；`T=1e6` 归零；精确尺寸对照证明是 1.0.2.0 既有问题）保留
在 `PROGRESS.md`「〇-最新、1.0.3.0 变更」第 (4) 节。

**1.0.4.0 的两条更正**（当时的推论漏洞，必须记住）：

1. `T=1e6` 归零**不能**把范围收窄到「除法」。`invT=1e-6` 同样会把 amp 双线性的
   1 ULP 压到 1e-14 量级、不影响 `gw`。据此做的一次 `y·(2−den·y)` Newton
   精化无效，是推论错误 + 残差抵消共同造成的，不是「除法无关」。
2. fxc 反汇编 `CSCompose` 生成的是 `div [precise]`，**不是 `rcp`**。「SM5 用近似
   倒数」这个推测作废。真正可疑的是驱动把 `div` 展开成硬件倒数序列时，极少数
   分母与 x86 `divss` 的正确舍入差 1 ULP —— **仍是推测**，没有 GPU 中间量回读，
   只能靠「精化后归零」反推。

定位改走**零 GPU 改动**的 CPU 侧 ULP 敏感度扫描（`composeTrace()`）：差异像素
CPU 复算 `outv = 156.500000000`，恰在 `+0.5` 边界；8 个中间量各 ±2 ULP 扰动，
**只有 `gw` 的 +1 ULP 翻成 156**。修法与回归见第 11 节。
`churnCheck` 的逐字节断言**从未放宽**，那个 `[KNOWN-1LSB]` 打印点现作回归哨兵。

## 11. 1.0.4.0 补充施工记录（2026-11-06）

### (1) 修法

`CSCompose` 里 `gw = 1.0f / (1.0f + ap)` 改为：

```hlsl
precise float den  = 1.0f + ap;
precise float invD = 1.0f / den;
float e = mad(-den, invD, 1.0f);   // 融合乘加算残差，保留低位
invD = invD + invD * e;
e = mad(-den, invD, 1.0f);
invD = invD + invD * e;
precise float gw = invD;
```

不动 CPU 生产基线（用户红线）。fxc 反汇编确认指令序列是
`div [precise] → mad / mul / add ×2`，全程 `[precise]`，没有被优化掉。

### (2) 两个坑

- HLSL 变量名不能叫 `y`：`CSCompose` 里已有 `int y = g_imgY0 + (int)id.y`，
  用 `precise float y` 会报 `X3003: redefinition of 'y'`。1.0.3.0 与 1.0.4.0
  各踩一次，改叫 `invD`。
- **一次 `y ← y·(2 − den·y)` 的 Newton 无效**：`2 − den·y` 有灾难性抵消，
  残差必须写成 `mad(-den, y, 1)` 且做**两次**。
