## 0. 摘要

**一句话**：磨皮从 CPU 的 71.5 ms（4K）压到 8.97 ms，且**输出与 CPU 版逐字节相同**，18 条 md5 基线一条都没改。

只需要记住五条：

| # | 结论 | 详见 |
|---|---|---|
| 1 | 收益全在**搬运**，不在计算：4K 上传 2.93 + 读回 3.24，而 5 个 kernel 的计算只有 0.27 ms | §5.1 |
| 2 | ROI 外扩量是**硬需求** `passes×32 + passes×(r2+ra) + 2`，少 `passes×32` 会稳定差 1~2 灰阶 | §3.2 |
| 3 | 精度标准是"严格逐字节 0 差异"，靠整数域盒式 + `precise` + `gw` 两次 Newton 精化达成 | §3.1、§3.3 |
| 4 | 纹理按 **64 对齐的容量式桶**分配，判据是"够用且不超需求 2 倍"，否则 ROI 每抖 1 px 就重建一整套 | §2.2 |
| 5 | 不许动宿主的 GPU 策略：不传 `DISABLE_GPU_TIMEOUT`，管道里不插 fence | §4 |

## 1. 被加速的是什么

### 1.1 生产默认路径：`surface3RgbBand`，四个阶段

面板默认 `blurType=0`（双边）→ `g_cfg.s3Band=1` → `surface3RgbBand`（`beauty_smooth.cpp:1128`，1.3.5.0 行号；施工时为 `:1087`）。

```
src (RGBA8 全帧)
  │
  ├─ Stage 0  下采样 2×2 盒式 → 3 个 float 平面 (ww×wh)，值域 0..255
  │            ww,wh = ceil(w/2), ceil(h/2)；不足 8 像素则保持原分辨率
  │
  ├─ Stage 1  B1 = bandBoxN(src, r1, nPass)     ← 窄模糊，可分离 H+V
  ├─ Stage 2  B2 = bandBoxN(src, r2, nPass)     ← 宽模糊，r2 保证 > r1
  ├─ Stage 3  amp = bandBoxN(|C.g − B2.g|, ra)  ← 只测绿通道
  │
  └─ Stage 4  上采样回全分辨率 + 逐像素合成：
              surfaceKeep 软膝 + 振幅门控 + I/e + skin 混 + 眼保护 → dst (RGBA8)
```

三个决定了"能搬到 GPU"的性质：

- 四个阶段**全是局部算子**，无跨像素依赖（盒式模糊看似有邻域，但已拆成 H/V 两趟）；
- 中间数据是 float 平面，尺寸只有全帧的 **1/4**（半分辨率）；
- 合成阶段需要 `mask`（掩码）和 `protect`（五官保护）两张**全分辨率 8bit 图**。

**半径必须由 `bandBoxW(ww, factor, minR)` 现算**，与分辨率绑定。GPU 侧要调同一个函数求半径，**不能在 shader 里另算**，否则两边核不一样。

### 1.2 开工前钉死的两个事实

| 旧记录 | 实际 |
|---|---|
| "磨皮 band 路径未 ROI 化，4K 70.7 ms 里 80% 是脸外白算" | **一半对**。`surface3RgbBand` 收了 `roi` 参数却**从未使用**（函数体只在 `roi.empty()` 处引了一下），确实是全帧算 —— 但 4K 的 70.7 ms 是 GPU 全帧**搬运**成本，CPU 磨皮是 71.5 ms，两个数不是一回事 |
| "磨皮 21 趟" | 那是 `surface3Rgb25` 那条路的说法。**生产默认走 `s3Band=1`**，结构比 21 趟简单得多 |

第一条差点让人去做一件已经做完的事 —— 这就是它要写下来的原因。

> `roi` 参数形同虚设这件事，1.0.6.0 已修（CPU 路径真按 roi 裁剪，逐字节不变）。实测收益**只有 1.3~3.4×**，典型人脸（1080p / roi 22%）仅 **1.5×**——早期"估算 4~6×"只算了面积比、没算 halo。且它只在 CPU 回落路径有效，`gpu_smooth=auto` 时生产根本不走 CPU。

## 2. GPU 怎么切

### 2.1 五个 kernel

Stage 1/2/3 共用同一个 box shader，靠参数区分：

| kernel | 输入 | 输出 | 说明 |
|---|---|---|---|
| `CSDown` | RGBA8 SRV | 3 × `RWTexture2D<float>`（或 1 张 `float4`） | 2×2 平均，边界 clamp |
| `CSBoxH` | float | float（临时） | 滑动窗口，每行独立 |
| `CSBoxV` | float | float（临时） | 同 `CSBoxH`，转置 dispatch |
| `CSAmp` | C.g, B2.g | float | `abs()` 后立刻接 boxH/V |
| `CSCompose` | C, B1, B2, amp, mask, protect | RGBA8 UAV | 逐像素，含 `surfaceKeep` |

> 另有 `CSBox2D`（1.3.3 把 H+V 合成一趟的实验），**默认关**，`BEAUTY_GPU_BOX2D=1` 才启用。它数值正确但**无性能收益**，结论见 `reference-performance.md` §3.2。

### 2.2 资源：ROI 尺寸 + 64 对齐的容量式桶

逻辑尺寸与分配尺寸必须分开，否则 ROI 抖一个像素就要重建一整套纹理：

```
逻辑尺寸（cbuffer / dispatch / clamp / 读回矩形）
   imgRW, imgRH, pw, ph        ← 每帧由 bbox 推出，可以逐帧变化
分配尺寸（CreateTexture2D / CopyResource / RowPitch）
   aImgW = (imgRW/64 + 1)*64   ← 始终多留一档，抗桶边界抖动
   aPw   = (pw/64   + 1)*64
   判重：fits = 现有纹理 >= 请求 且 不超过请求 2 倍
```

三个坑，都是台架逼出来的，别走回头路：

1. **只用标准 ceil 不够**：640 正好整除 64，余量为 0，抖到 641 就跨桶，来回抖等于每帧重建。所以是 `(v/64 + 1)*64`。
2. **只做"桶相等才复用"也不够**：640×394 与 644×398 两个实例交替时，20 轮 40 次调用重建了 39 次。必须改成容量式（`>=`）。
3. **不能无限复用大纹理**：4K 切回小图后每帧仍会 `CopyResource` 整张 4K，所以加"超过需求 2 倍就收缩一次"。

`gpuSmoothDebugPlane()` 的 staging 必须用**桶尺寸**（`CopyResource` 要求尺寸一致），但只把左上角真实 `pw×ph` 拷给调用方，桶外填充像素不算逻辑数据。

显存量级：4K 人脸 ROI 按 1280×1440 估，半分辨率 640×720 = 46 万像素，单平面 1.8 MB，同时活着约 10 个平面 = 18 MB。

### 2.3 为什么不做全帧

`gpu_beauty.h` 实测 4K 全帧搬运 70.7 ms，与 CPU 持平，全无收益；ROI 搬运只要 3.60 ms（RGBA8 口径）。**必须沿用 ROI 通道**，这不是优化选择，是可行性前提。

## 3. 决策一：精度必须逐字节（标准 A）

**用户拍板 A：严格 0 字节差异，不许改基线。已达成，四画幅全 0。**

### 3.1 为什么可能：整数域盒式

盒式模糊是 `Σ(整数) / n`，输入是 0..255 的整数，float 累加在 2^24 以内精确无误差，IEEE754 除法是确定性的。剩下的风险只有两处，都已处理：

| 风险 | 处理 | 状态 |
|---|---|---|
| 编译器把 `a*b + c` 融合成 FMA，CPU/GPU 融合方式不同 | 所有合成表达式加 `precise`，禁 FMA/mad 收缩 | 已做，0 位差 |
| `div` 展开后与 CPU `divss` 在极少数分母上差 1 ULP | `mad` 残差 + 两次 Newton 精化 | 已做，见 §3.3 |

### 3.2 硬约束：ROI 外扩必须含 `passes × 32`

```cpp
const int growP = passes * 32 + passes * (r2 + ra) + 2;
//               ↑ 新增项        ↑ 模糊传播        ↑ 双线性
```

**为什么 `passes × 32` 是硬需求**：`bandBoxH/V` 每 32 像素用"从头重算窗口和"纠正 float 累加误差（`kFlush = 32`）。由此产生一条污染链：

- ROI 最外一块（局部 x=0）重算窗口时左边**没有数据**，只能 clamp 到自身；
- 整帧版同一像素重算时，左边读到的是**真实邻居**；
- 于是 ROI 最外一块**整块**的窗口和与整帧不同；
- 下一块重算要读左邻 r 个像素 → 污染向内容方向传染**一块**；
- 一共传染 `passes` 次 → 污染半径 = `32 × passes`。

**证据链**（ROI 内缩扫描 `[SCAN]`，1080p 横，单位：字节差异数）：

```
inset  32:12038   44:7723   64:1613   96:0   128:0   160:0
                                    ↑ 归零，恰等于 32 × passes(3) = 96
```

修复前 `growP = passes*(r2+ra)+2 = 20`，连一个 32 周期都不够。按 1080p 的 `r1/r2/ra = 2/4/2`、`passes=3` 代入，现在是 `96 + 18 + 2 = 116`。

**排除法**（全部实测 0 位差，用于证明"不是别的原因"）：

| 对照项 | 结果 | 排除了什么 |
|---|---|---|
| `C 平面`（下采样） | 0 位差 / 106400 点 | 上传、下采样、坐标映射 |
| `gpu vs refG` / `gpu vs refP` / `refG vs refP` | 全 0 位差 | GPU 算式与两路算法复刻 |
| `cpuBox(direct) vs prod` | 0 位差 / 494656 点 | CPU 生产结果可被直接复现 |
| `cpuBox t=1 vs t=12` | 0 位差 | 并行无竞态 |
| `passes=1/2/3 refP vs cpuBox` | 全 0 位差 | 单趟与多趟结构 |
| `cpuBox(crop) vs refP` | 0 位差 | 裁剪输入的 box 段同构 |

排到最后只剩"ROI 与整帧的边界"，扫描一测即中。

#### 二次踩坑：夹具假象让这个常数被误改过一次

1.1.2.0 曾把它改成常数项 `32`（不乘 `passes`），理由是"台架上 1080p 首个零差异档只到 8"。**那是夹具假象**：那几组合成蒙版的包围盒贴着画幅边缘，`plx0` 被 clamp 到 0，局部 x=0 恰好就是整帧边界，clamp 与真值相同 → 边距再小也不出错。

换成 1074×604 的真实素材跑黄金基线，立刻现形：`growP ≤ 52` 时 `blur100` 稳定差 1 字节，`64` 才归零——而 `blur100` 的门控阈值最大、磨皮权重最满，正是最能把 1 LSB 放大的档。

**结论**：`32 × passes` 是"污染传染 passes 块"的结构性下界，只有改 flush 方案（让首块读到真邻居）才能去掉，压常数项做不到。

> 代码里留了 `g_growPForTest` 消融钩子（`BEAUTY_TEST_HOOKS` 构建才存在，生产构建无此符号），就是给这类扫描用的。

### 3.3 compose 的 1 ULP：`gw` 的两次 Newton

`churnCheck` 400 帧里第 336/337 帧各差 1 字节（`(254,130)` R 通道，`157` vs `156`）。定位走**零 GPU 改动**的 CPU 侧 ULP 敏感度扫描（`composeTrace()`）：差异像素 CPU 复算 `outv = 156.500000000`，恰在 `+0.5` 边界；8 个中间量各 ±2 ULP 扰动，**只有 `gw` 的 +1 ULP 翻成 156**。

修法（不动 CPU 生产基线）：

```hlsl
precise float den  = 1.0f + ap;
precise float invD = 1.0f / den;
float e = mad(-den, invD, 1.0f);   // 融合乘加算残差，保留低位
invD = invD + invD * e;
e = mad(-den, invD, 1.0f);
invD = invD + invD * e;
precise float gw = invD;
```

fxc 反汇编确认序列是 `div [precise] → mad / mul / add ×2`，全程没有被优化掉。修完 churn 400 帧 `diff=0`，台架回到 **7/7**。

**两个坑**：

- HLSL 变量名不能叫 `y`：`CSCompose` 里已有 `int y = ...`，`precise float y` 会报 `X3003: redefinition of 'y'`（两次踩到，改叫 `invD`）。
- 一次 `y ← y·(2 − den·y)` 的 Newton **无效**：`2 − den·y` 有灾难性抵消，残差必须写成 `mad(-den, y, 1)` 且做**两次**。

### 3.4 台架方法学的两个错误（判据本身的错，不是实现的错）

**错误一：`runBox` 已经是一整趟（H+V），循环里再调两次 = 跑成 `2×passes` 趟。**
第一版就这么写的，`passes=3` 变成 6 趟，模糊半径直接翻倍，画面差 9~14 灰阶。是离线台架一次对出来的 —— 这类错在 Resolve 里只会表现为"效果好像变强了"，根本定位不到。

**错误二："裁剪对拍"从设计上就不成立。**
台架原有一项把 GPU 实际处理的矩形裁出来交给 CPU 重跑，想用它区分"算法错"与"halo 不足"。但 `bandBoxW` 的半径是**按画面宽度比例**算的：

```cpp
int k = (int)(frac * ww + 0.5f);   // ww 是半分辨率宽度，裁小了它跟着变小
if (k < minW) k = minW;
if ((k & 1) == 0) k++;             // 半径必须是奇数宽
```

裁剪之后算出的 r 可能与全帧不同 —— 裁剪版 CPU 跑的是**另一组参数**。四个画幅完全吻合这个解释：

| 画幅 | 全帧 r1/r2/ra | 裁剪后 r1/r2/ra | 裁剪对拍 |
|---|---|---|---|
| 1920×1080 | 2/4/2 | **1/2/1** | 有差异 |
| 3840×2160 | 5/9/5 | **2/4/2** | 有差异 |
| 1080×1920 | 1/2/1 | 1/2/1（恰好相同） | **0** |
| 640×394 | 1/2/1 | 1/2/1（本来就是全图） | **0** |

"裁剪对拍 = 0"的两个画幅，恰好是半径没变的两个。该项现在标注为**参考项，不计入判定**，并在日志里同时打印两边实际 r 值。

## 4. 决策二：不改变宿主的 GPU 策略

两条都是"插件不该替宿主做决定"的原则问题，与是否真的导致某次崩溃无关。

### 4.1 去掉 `DISABLE_GPU_TIMEOUT`

`createDevice()` 的 `D3D11CreateDevice` flags 改为 `0`。原先传 `D3D11_CREATE_DEVICE_DISABLE_GPU_TIMEOUT` 会**关掉 GPU 超时重置**，而 Resolve 与本插件共用同一块 GPU。同时删掉"失败后去掉该 flag 重试"的兜底（首选已不带 flag，兜底没有意义）。

### 4.2 管道里不插 fence

沿用早期 GPU 渲染管道（P1）的结论：不在管道中插任何显式 fence，只留一次 `Map(READ)` 自然阻塞。Optimus 笔记本上显式同步会带来跨适配器卡顿。

## 5. 验证数据

### 5.1 四画幅逐字节（合成图，含 mask/protect，带宽已计入上传与读回）

| 画幅 | CPU `surface3RgbBand` | GPU 合计 | 上传 | 计算 | 读回 | 逐字节 |
|---|---|---|---|---|---|---|
| 1920×1080 | 24.6 ms（8 线程） | **3.13 ms** | 1.30 | 0.38 | 0.90 | **0 字节** ✔ |
| 3840×2160 | 71.5 ms（8 线程） | **8.97 ms** | 2.93 | 0.27 | 3.24 | **0 字节** ✔ |
| 1080×1920 | 24.6 ms | **2.73 ms** | 0.82 | 0.17 | 1.15 | **0 字节** ✔ |
| 640×394 | — | **0.84 ms** | 0.19 | 0.20 | 0.39 | **0 字节** ✔ |

4K 8.0×、1080p 7.9×。**计算段只有 0.17~0.38 ms，瓶颈完全在数据搬运。**

"合计"比"上传+计算+读回"多出的一截是 **ROI 外补齐**：GPU 只写输出矩形，矩形外的 dst 必须补成 src（CPU 版是整帧逐像素写）。4K 约 2.5 ms（输出矩形占 34%，补 66%），1080p 约 0.55 ms。若调用方能让 `dst` 与 `src` 同址，这段整段跳过。

> CPU 列是 1.0.1.1 时期的 8 线程实测，此后未复测（GPU 相关工作未触碰 CPU 路径）。

### 5.2 台架用例与硬判据

`_p2bench/gpu_smooth_test.cpp`，判据来自 `gpuSmoothResourceStats()`（重建次数、设备创建次数、当前桶尺寸）：

| 用例 | 硬判据 |
|---|---|
| ROI 逐帧抖动 400 帧 | `rejects=0`、`diff=0`、`deviceCreate=0`、`rebuild<=2`、`reuse==sizeChanges` |
| 多实例交替 | `rejects=0`、`diff=0`、`deviceCreate=0`、同桶 `rebuild<=2`、跨桶 `rebuild<=2`、`ready=true` |
| 生命周期 | 同尺寸连续 3 次 + shutdown 后 2 次，全程不得出现设备重建 |

实测：`[A-OK] rebuild=0 deviceCreate=0 reuse=69/69 rejects=0`；`[MULTI] sameBucket rebuild=0 ; crossBucket rebuild=1`；台架 **7/7 全绿**。

### 5.3 真机长时（27 分钟 / 18478 帧）

| 项 | 结果 |
|---|---|
| 会话 | `onLoad build=1.0.4.0` → `unload：释放引擎` 正常收尾，约 27 分钟 |
| 帧数 | 18478 帧 |
| GPU 磨皮均合计 | **3.28 ms**（1.0.2.0 同期 6.28 ms） |
| 单帧插件总耗时 | 14.2 ~ 18.0 ms（30 fps 预算 33.3 ms，做完即空等） |
| ROI 抖动 | 持续变化，容量式桶化稳定承接，无重建风暴 |
| GPU→CPU 回落 | **0 次** |
| 异常 | `DEVICE_REMOVED` / `DEVICE_RESET` / `exception` / `failed` 全无 |

**判读坑**：`grep 回落` 会命中 `参数 blur_level 是非有限值（NaN/Inf），已回落默认 50`——那是参数校验，不是 GPU 渲染回落。判断 GPU 回落要看 `GPU 磨皮` 行的连续性 + `DEVICE_*` / `failed` 关键字。

### 5.4 接入时抓到的真 bug：`g_ready` 从未赋值

`gpuSmoothRgbBand` 开头 `if (!g_ready && !createDevice())` **忘了在成功后给 `g_ready` 赋值** → 每次调用都重建设备、纹理留在旧设备 → 第二次 `Map` 返回 `DXGI_ERROR_DEVICE_REMOVED`，表现成"首帧好用、之后每帧静默回退 CPU"。

台架四个画幅尺寸各不相同，恰好把这个问题盖住了；是 `mock_host.py` 的**多实例序列**抓到的。这也是 §5.2 补"生命周期"用例的直接原因。

> 教训：台架**只有单次调用**时，设备生命周期类缺陷一律不可见。

## 7. 已作废的说法（别再引用）

| 旧说法 | 现状 | 依据 |
|---|---|---|
| "4K 磨皮 5.52 ms / 4.04 ms" | 都不含 ROI 外补齐：4.04 是外扩量还少 `passes×32`（`halo=20`）的时期，5.52 是外扩已补齐但 `dst` 预填了 src 的时期。**以 §5.1 的 8.97 ms 为准** | §5.1 |
| "剩余 2~3 字节差异是 1 ULP 翻越 .5 边界、驱动 ISA 选择不可控" | 错。真正原因是 ROI 外扩少了 `passes × 32` | §3.2 |
| "`growP` 常数项取 32 就够（台架 1080p 已归零）" | **夹具假象**：包围盒贴边使 `plx0` clamp 到 0。真实素材 1074×604 上 `blur100` 差 1 字节，必须乘 `passes` | §3.2 |
| "裁剪对拍可以区分算法错与 halo 不足" | 裁剪会改变 `bandBoxW` 算出的半径，CPU 跑的是另一组参数。已降为参考项 | §3.4 |
| "`surface3RgbBand` 的 `roi` 参数生效" | 1.0.6.0 之前**从未被使用**，全帧计算 | §1.2 |
| "CPU 磨皮 ROI 化能省 4~6×" | 只算面积比、没算 halo。实测典型人脸仅 1.5×，小脸与 4K 才 4.2~5.9× | §1.2 |
| "SM5 用近似倒数 `rcp` 算 `1/(1+ap)`" | fxc 反汇编是 `div [precise]`，不是 `rcp` | §3.3 |
| "`T=1e6` 归零能把范围收窄到除法" | 错。`invT=1e-6` 同样把 amp 双线性的 1 ULP 压到 1e-14 量级，与 `gw` 无关 | §3.3 |
| "`gpu_smooth` 出厂默认 `off`" | 1.0.8.0 起出厂默认 **`auto`**（首帧自检一次，之后零开销） | `reference-architecture.md` §5.1 |
