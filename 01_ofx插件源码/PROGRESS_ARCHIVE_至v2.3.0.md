## 本轮（阶段 1–3）改了什么

### 阶段 1 —— 可验证性

新增插件自带日志 `ofxLog()`，落 `C:\ProgramData\NamaBeauty\logs\ofx.log`：

- 线程安全（CRITICAL_SECTION），4MB 上限，超限整文件重来
- 记录 `onLoad`（含宿主名）/ `describe` / `describeInContext` /
  `createInstance`（含引擎预热结果与耗时、ownerTid）/ 每个 render 的
  尺寸、像素深度、rowBytes、人脸数、**分段耗时**、draft/interactive/seq 标志
- 默认详细记前 8 帧 + 每 120 帧一条；`NAMA_OFX_LOG_ALL=1` 逐帧；
  `NAMA_OFX_LOG=0` 关闭；`NAMA_OFX_LOG=<路径>` 改位置

### 阶段 2 —— 稳定性

| # | 问题 | 处理 |
|---|---|---|
| 1 | `renderMain` 用 `srcRect` 算宽高却写进 `dstPtr`，忽略 `dstRect` | 改为分别取 src/dst bounds，取交集，不一致时记警告 |
| 2 | 八项全 0 仍要走完整 SDK 链路 | 短路透传（逐字节 memcpy）+ 新增 `kOfxImageEffectActionIsIdentity` |
| 3 | 1842 ms 引擎初始化落在渲染线程首帧 | 挪到 `createInstance` 预热，并提供 `lastSdkMs()` 计量 |
| 4 | SDK 一旦抛访问违例会带崩 Resolve | 所有 SDK 入口包 `__try/__except`，崩溃后标记 `poisoned_` 本进程内不再调用 |
| 5 | 初始化失败后每帧重试，每帧重付 2.5 秒 | 失败计数上限 3 次 |
| 6 | `wglMakeCurrent` 失败被静默忽略 | 检查返回值；失败时不执行还原（避免无意义的切回） |
| 7 | 参数未变仍每帧下发 10 次 setter | 缓存上次应用的 `NamaSettings`，未变则跳过 |

### 阶段 3 —— 性能

| # | 改动 | 效果 |
|---|---|---|
| 1 | 像素缓冲从每帧 `std::string::assign` 改为**按渲染线程复用** | 1080p 每帧省两笔 8MB 分配/释放 |
| 2 | `float32 ↔ RGBA8` 转换改 AVX2 内联函数 + 标量兜底 | 1080p 单程约 0.8 ms（8bit）/ 3.5 ms（float） |
| 3 | `build.bat` 加 `/arch:AVX2 /std:c++17` | — |

**线程局部缓冲刻意不用 `thread_local std::vector`**：那是带析构函数的线程局部对象，
宿主 `FreeLibrary` 之后若有线程退出，DLL 里的析构函数指针会悬空。
改成 `__declspec(thread)` 存裸指针、指向刻意不释放的分配，进程退出交给 OS 回收。

## 已知的「没做」

- **未实现的动作**：`kOfxImageEffectActionGetClipPreferences`（让输出深度跟随输入，
  可再省一次转换）。因为没有真实宿主可验证，宁可不做也别做错。

## 已定的设计决策（别改回去）

- **sharpen 默认 0**：源码 g_params[] 里是 20，但实测磨皮非 0 时锐化恒无效果，给 0 才诚实。
- **全局滤镜永久关闭**（2026-10-20 改）：`filter_name="origin"`、`filter_level` 恒 0。
  以前是「八项全 0 时为 0，否则 0.4」，那会让磨皮一开就整帧提亮（详见文末修复记录）。

- **支持 float**：降到 8bit 处理再升回去，有损但保证 Color 页面能加载。
- **不做 Rust 版**：本机无 Rust 工具链；OFX 是 C ABI，Rust 不解决本次三个真难点。
- **Lua 脚本版已移出菜单**（`C:\ProgramData\NamaBeauty\disabled_scripts\`），
  代码保留但不再维护，两条路线只留 OFX 一条。

## 2026-10-14 22:30 播放定格 bug 修复（build 1.3）

**现象**：剪辑页/调色页挂上插件后播放，预览窗画面不动、声音照常。

**根因**：`renderMain` 向宿主取图时把时间写死成 `0.0`：

```cpp
// 修复前
gEffectHost->clipGetImage(outputClip, 0.0, &region, &outputImg);
gEffectHost->clipGetImage(sourceClip, 0.0, &region, &sourceImg);
```

render 动作 inArgs 里的 `kOfxPropTime` 是「这一次要渲第几帧」。不读它、传 0.0，
等于播放头走到第 N 帧我们仍向宿主索要第 0 帧 —— 画面自然定格在第一帧。

**修复**：读 inArgs 的 `kOfxPropTime`，原样传给两次 `clipGetImage`；
顺带读 `kOfxImageEffectPropRenderScale` 用于诊断。日志加 `time=%.3f scale=%.2f`。

**回归**：`mock_host.py` 增加「每帧不同时间」断言（96.5 / 103.75 / 111.0 / 118.25），
写死 0.0 会立刻判红；连续帧测试不再复用同一个 inArgs。

**顺带修的两个真问题**

1. 夹具 `mock_host.py` 没实现 `propGetDoubleN`，套件槽位是 0，插件一调用就空指针崩溃。
2. `install.bat` 先 `rmdir /s /q` 目标目录再 xcopy。Resolve 锁着 DLL 时删不掉 DLL，
   但 `model/`、`graphics/` 被删成功、xcopy 又整体失败没拷回 → 安装目录半空 →
   引擎报「资源文件缺失」并**静默降级为透传**（美颜完全不生效，界面不报错）。
   新脚本改为逐文件替换，锁住的文件先 `move` 改名（Windows 允许重命名已映射文件）再 copy，
   最后逐项校验。注意 .bat 必须是 CRLF，LF 会让 cmd 把 `rem` 当命令执行。

**验证**：1920x1080 基准 20.2ms/帧 ≈ 49fps；插件日志 `render #4 time=118.250` 确认时间已透传。

## 2026-10-20 23:55 磨皮给整帧加亮度（build 1.3 同版本号，修 bug）

**现象**：把「磨皮」从 0 拉到任意非 0 值，画面整体变亮 —— 不只是人脸，背景、衣服、
字幕全都跟着亮。

**根因**：`nama_engine.cpp` 里照抄了 obs-nama-beauty.cpp 的全局滤镜设置：

```cpp
sehSetParamd(item, "filter_level", anyEffect ? 0.4 : 0.0);
```

`anyEffect` = 八项里任意一项 > 0。于是磨皮从 0 拉到 1 的瞬间，`ziran2` 滤镜
（强度 0.4）被打开，而它作用于**整帧**。滤镜不是中性的，它是一条抬暗部的曲线。

**实测证据**（640×394 纯灰 128，无人脸，逐字节比对）：

| filter_level | 输出均值 RGB | 相对输入 |
|---|---|---|
| 0.0 | 128,128,128 | +0,+0,+0（逐字节不变） |
| 0.1 | 132,131,131 | +4,+3,+3 |
| 0.2 | 136,135,135 | +8,+7,+7 |
| 0.4 | 144,142,142 | **+16,+14,+14** |

灰阶 ramp 上（filter_level=0.4 相对 0.0）：输入 25→34、128→144、229→230。
典型的「抬暗部 + 压高光」曲线，整幅画面的对比度被压缩。

**修复**：滤镜永久关闭，`filter_name="origin"`、`filter_level` 恒 0。
`anyEffect` 变量连同它的语义一并删掉，避免后人再按「有参数就开滤镜」的直觉改回去。

```cpp
sehSetParams(item, "filter_name", kFilterName);   // "origin"
sehSetParamd(item, "filter_level", kFilterLevel); // 0.0
```

**验证**（修复后，同一纯灰帧）：磨皮 0 / 1 / 70 / 100 全部 `+0,+0,+0`，maxdiff=0。
八项效果本身不受影响：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 纯灰 + 磨皮 70 | +16,+14,+14（全是滤镜） | +0,+0,+0 |
| 棋盘格 + 磨皮 60 | mean 128→140.8, stdev 60→52.6 | mean 128→128.0, stdev 60→56.2 |
| 纯灰 + 美白 15 | +21,+18,+17 | +5,+5,+4 |
| 纯灰 + 美白 100 | +48,+43,+38 | +36,+32,+26 |
| 纯灰 + 清晰 100 | — | +6,+6,+6 |
| 纯灰 + 红润 100 | — | +2,-3,-1 |

即：磨皮现在只降细节（stdev 60→56.2）不动亮度（mean 128→128.0）；
美白/清晰/红润仍按各自量级生效，只是不再额外叠加那层全局提亮。

**测试夹具同步修**：`mock_host.py` 原来的 8bit 用例用**平滑渐变**做素材，喂给
磨皮后逐像素差只有 1~2 —— 它之所以一直 PASS，靠的正是全局滤镜把整帧提亮
（blur=60 时改动占比 98.89% 全部来自滤镜，关掉滤镜后是 0.00%）。属于结构性假阳性。
本轮改动：

1. 素材改为带高频颗粒的纹理帧（`_make_textured_frame`），磨皮才有细节可磨；
   磁盘素材缺失或尺寸不符时自动合成，不再依赖外部 `probe_in.raw`。
2. 新增用例 **B10「磨皮不改变整体亮度」**：比较 blur=0 与 blur=60 的平均 RGB，
   漂移须 ≤1.0；同时要求细节能量（相邻像素差均值）下降 ≥2%，确保磨皮真的生效。
   这两条一起才能区分「磨皮生效」与「整帧提亮」。

**回归**：`mock_host.py` 15 项全 PASS（新增 B10）。用备份的旧版二进制跑同一套夹具，
只有 B10 FAIL（漂移 13.14），其余 14 项 PASS —— 说明新断言精准命中本 bug，
且没有把别的行为带坏。

**注意**：`NAMA_OFX_DLL` 指向 `out\NamaBeauty.ofx` 时必须同时设 `NAMA_ENGINE_DIR`
指向装了引擎资源的目录，否则 `LoadLibrary CNamaSDK.dll` 失败、`slot=-1`，
所有「改动画面」的用例都会因为根本没跑 SDK 而假红。

即：开启后背景、衣服基本不动，皮肤区域照常磨。**没有引入亮度问题**（和上一轮
filter 修复可以叠加使用，两者互不干扰）。

**改动**：三处默认值统一改成 1
- `nama_engine.h`：`NamaSettings::skin_detect` 初值 0 → 1

把 `kOfxParamPropDefault` 当成「用户第一次拖上效果看到的状态」来断言，
防止默认值再被悄悄改回 0。

## 2026-10-21 10:00 通道序修复：SDK 按 BGRA 读缓冲（build 1.3 同版本号）

**现象**：用户反馈「还是全局磨皮了」—— 上一轮把 `skin_detect` 默认打开后仍然如此。

**根因**：`FU_FORMAT_RGBA_BUFFER = 0` 这个常量值本身没错，但这个 SDK 版本
按 **BGRA byte order** 解释 format 0 的缓冲区。引擎一直把宿主给的 RGBA 直接
交给 SDK，于是 AI 模型看到的是 R/B 反过来的脸 —— 颜色错乱，人脸检测基本失效。

**证据链**（同一张照片 A7300538，640×394，同一次初始化，只改通道序）：

| 输入通道序 | `fuFaceProcessorGetNumResults` |
|---|---|
| R,G,B,A（原样） | **0** |
| B,G,R,A（交换 R/B） | **1** |

43 张真实照片的统计：修之前 **4/43** 检出人脸，修之后 **11/43**
（`{0:32, 1:7, 2:3, 3:1}`）。剩下 32 张是远景大场景，人脸在画面里占比太小，
属于正常的检测限制，不是 bug。

**修复**：在 SDK 边界上做 R/B 交换，插件其余部分仍然一律 RGBA。
- 输入侧：`src` 复制到 `bgScratch_` 后 `rgbaToBgra`（不能原地改，调用方可能复用）
- 输出侧：SDK 写完后 `bgraToRgba`，再交给调用方
- ⚠️ 踩过的坑：`out` 缓冲同时承担两个角色（SDK 的输出缓冲 + 没写满时的兜底内容），
  曾经在 memcpy 后和渲染后各交换一次，等于交换两次，**输出颜色是反的**。
  现在只在 SDK 写完之后交换一次。

**验证**：
- 阶梯边缘探针（左半 R=255 / 右半 R=0，G 恒 128）：左右两半色相保持不变，
  红还是红、蓝还是蓝，边缘抹开可见 —— 通道序正确且磨皮生效。
- 新增夹具用例 **B12「通道序 RGB 不被交换」**，用同一张阶梯图断言色相不被换掉。
- `mock_host.py` **17 项全 PASS**（B10 亮度 / B11 只磨皮肤默认 / B12 通道序）。
- 安装版与编译产物 SHA256 一致。

**方法论备注（踩过两次，值得记下来）**：
1. 夹具里新建局部 `SRC_BUF/DST_BUF` 是**局部变量**，不会覆盖模块级全局 ——
   插件通过 `clipGetImage` 读的是全局那份，量到的会是上一次渲染的缓冲。
   写回全局才会生效。
2. 小画幅（64×64）会撞 `isThrowawayRender` 的面积兜底（< 源 RoD 的 1/16 直接透传），
   根本进不了 SDK，量到的只是源数据本身。通道序这类用例必须用全画幅。

本轮不改产品行为（除了美白实现和两处真 bug），目标是「跑得动、测得准、装得上」：
先把基线跑通，再定位性能与精度问题，修完复测，最后用**安装后的二进制**再回归一遍。

### 1. 基线

- `build.bat` 干净编译通过（MSVC 14.51.36231 / Windows SDK 10.0.26100.0），无新增 warning。
- `mock_host.py` 原 18 项全 PASS；`selftest_ofx.py` 渲染 / 全 0 透传 PASS。

  `NamaVersion()` 运行时返回 **65540 = 0x10004**。

### 2. 美白掩码性能：38.2 ms → 4.5 ms（1080p，8.4 倍）

**基线与定位**（`beauty_probe\bench_whiten.py`，同一帧只切 `color_level`）：

| 场景 | 1080p 掩码耗时 |
|---|---|
| 首版实现（color_level=0） | 24.6 ms |
| 首版实现（color_level=100） | 62.8 ms |
| 首版实现（默认 15） | **38.2 ms** |

三个叠加的成本，全在每帧的热路径上：

1. 每帧 3 次堆分配（掩码 / 临时缓冲 / 提亮表）；
2. 每帧向 stderr 打调试信息（无宿主时尤其贵，且刷日志）；
3. 全分辨率逐像素算肤色距离 + 两轮 3×3 羽化。

**改法**：

- 掩码降到 **1/4 分辨率**（宽高各除以 4，1080p 约 13 万点）算肤色，再双线性放大回全分辨率；
- 羽化改成**可分离** 3×3（先横后纵，9 次采样降到 6 次），在低分辨率图上做；
- 提亮量预生成 **256 项整数表**（`tLut[]`），逐像素查表后只做整数乘加，不再每像素算浮点；
- 缓冲提升为引擎成员（`whitenMask_` / `whitenTmp_`），按需扩容、不再每帧分配；
- 删掉每帧 stderr 输出。

**复测**：默认参数下 **4.5 ms/帧**；美白=0 或 `faces=0` 时直接短路，不跑掩码。
端到端 8bit 仍是 13–16 ms 量级，SDK 依旧是大头。

### 3. 整数提亮表少除 255（B13 抓到的真 bug）

预生成表时把「0–255 的通道值 × 增益」直接当成了归一化系数，漏掉 `/255`，
导致提亮量被放大约 255 倍、再被 saturate 截断 —— 人脸区几乎全白。

修复：`tLut[i] = k * i * 16777216.0 / 65025.0`（`65025 = 255×255`，2^24 定点）。

**验证**：B13「无脸帧逐字节不变 + 人脸帧只轻微提亮」的人脸区平均差
**67.00 → 6.24**（默认 `color_level=15`）。同时给 B13 补了上限
`3.0 <= face_avg <= 30.0`，防止将来又把「过亮」当成 PASS。

### 4. 中文路径下自测失败（err=126）

`NamaSelfTest` 用 `LoadLibraryA` 加载引擎，传的是 UTF-8 的 `engineDir`；
非中文系统 ACP 下路径含中文时找不到模块，返回 126（ERROR_MOD_NOT_FOUND）。

修复：新增 `utf8ToAcp()`，`engineDir` / `rawIn` / `rawOut` 三个入口参数统一转 ACP 再调 Win32。
`selftest_ofx.py` 在本目录（`NamaBeauty_v1.51`）下重跑通过。

顺带：`selftest_ofx.py` 在 `probe_in.raw` 缺失时自动合成纹理帧，夹具自包含，
不再依赖外部素材。

### 5. 清掉「头部掩码」死代码

`fuFaceProcessorGetResultHeadMask` 在本机 SDK 上**恒返回 nullptr**（faces=1 时也一样），

`sehGetHeadMask`，相关注释从「头部掩码」改成「肤色掩码」，避免误导后来人。

**需求**：把「磨皮区域」「美白区域」判断逻辑查清楚并给优化方案。
本轮只做**探测**（不改产品行为），结论见

**新增探针（夹具目录）**：

| 文件 | 作用 |
|---|---|
| `probe_sdk_caps.py` | SDK 人脸信息 / 掩码 API / setter 能力矩阵（分步、子进程隔离） |
| `probe_blur_region.py` | 磨皮区域矩阵：合成帧（真人脸 + 非肤色 HF/BLUE + 假肤色 PALE/SKINTONE），支持 `--noface` / `--level` / `--cases` / `--no-file` |

| `probe_sdk_param_pool.py` | 打印 `CNamaSDK.dll` 里 `skin_detect` 前后的参数名池（隐藏参数清单来源） |

**结论 1 · SDK 不给任何区域数据（证书拒绝，不是签名问题）**：
`fuGetFaceInfo` 的 `face_rect`/`landmarks`/`expression` 返回 ret=0 且缓冲全 0，
日志 `this certificate don't have access to this parameter!` +
`Not granted permission to specific info`；`face_count`/`face_identifier` 等则明确
`Not supported face info`（说明**键名是 SDK 认出来的**，是权限/版本问题）。
`fuFaceProcessorGetResultHeadMask` 直接 `this certificate don't have access to this api!`。
唯一可用的是 `fuFaceProcessorGetNumResults()`（人脸个数，引擎已在用）。
可用的 setter：`fuFaceProcessorSetMinFaceRatio` / `fuSetFaceDelayLeaveEnable` /
`fuSetFaceDelayLeaveFrameNum`。

**结论 2 · 磨皮区域 = SDK 内部逐像素肤色掩码，只看颜色、不看人脸**：

* 画面里**完全没有脸**时掩码照样精确生效 → **与人脸检测无关**。
  （这条推翻了源码里 `ofx_plugin.cpp:545` 的旧注释「依赖人脸检测，faces=0 时无效」。）
* 没人脸的假肤色块被当皮肤磨掉（`PALE` 改动 88.5%、`SKINTONE` 96.9%）→
  「只磨皮肤区域」= **只磨肤色**，木桌/米色墙/手臂同样会被磨。
* 掩码是**软**还是**硬**，取决于「磨皮算法」而不是 `skin_detect`：

| 磨皮算法（面板） | 非肤色区域 | 说明 |
|---|---|---|
| 双边滤波（**当前默认**） | 仍被改动 93.3%、细节 −22% | 掩码是**加权**（肤色 ≈1.0、非肤色 ≈0.5） |
| 高斯 | **逐字节不变（0.0%）** | 真·硬掩码；代价是肤色内更狠（−76% vs −46%）且不保边 |
| 弱磨皮 | **逐字节不变（0.0%）** | 硬掩码且整体最轻（−37%） |

* 面板 20（当前默认强度）下结论不变：双边档非肤色蓝块仍被改动 **96.7%**。
  但**同一面板值下三档的强度完全不同**（肤色效果 双边 −55% / 高斯 −18% / 弱磨皮 −8%），
  所以「换默认算法」必须同时重标定默认强度，不能只改枚举。

**结论 3 · SDK 域内没有任何参数能把区域收紧到人脸**：
从 DLL 字符串池挖出的 13 个隐藏参数逐个实测，**只有 `blur_blend_ratio` 有效**
（未公开的强度混合比，Δ ≈ 3.0·√r，且在**高斯档下无效**）；
`nonskin_blur_scale`（0/1，文件源每帧 + 环境变量源创建时下发**都试了**）、
`blur_use_mask`、`debug_mask`、`blur_radius`、`change_frames`、`use_landmark`、
`heavy_blur`、`lower_quality` 以及 5 个假参数名**全部 no-op**，且 SDK 不报错。

**结论 4 · 美白没有任何区域化路径（全是整帧）**：
`color_level` / `color_level_v2` / `red_level` / `use_new_red` 全部整帧 ——
判据是「画面里放一块非肤色的蓝块」，结果改动 **100%**。
`use_new_whiten` 是**空开关**（`wl_new_v2_1` 与 `wl_v2_1` 逐字节相同）。
→ 插件把 SDK 美白恒关（`color_level=0`）、自己在 CPU 侧按肤色掩码做，是正确选择。
**`probe_whiten_v2.py` / `sweep_whiten.py` 文档里「A5 `use_new_whiten=1;color_level_v2=1`
→ 只在人脸」的旧结论已被推翻**，两个脚本顶部与「测量纪律」里都已标注更正
（当年拿 `skin_detect=1 vs 0` 的磨皮差分当人脸掩码，而磨皮掩码其实是肤色）。

**测量纪律（本次踩坑，已写进报告第 2.4 节）**：
① `NAMA_EXTRA_PARAMS_FILE` 必须在加载插件前设好，且要 `os.environ` +

③ 参数**粘住不复位**，扫参数必须逐例独立子进程 + 每例渲染两帧取第二帧；
④ 面板八项全 0 时插件**直接透传、SDK 根本没跑**，此时任何 SDK 参数都看不出效果。

**重要更正（复核日志后）**：不是「皮肤分割模型没加载」，而是**它一直在跑**。初始化日志里有
`Perform SetUseSkinSeg` 与 `Perform SetUseDelSpot`，说明人脸处理器每帧都在算皮肤分割，
成本已含在 11–15 ms 里。断点在**下游**：美颜道具的磨皮/美白着色器仍走 `USE_COLOR_MASK_OUT`
那条颜色判据，没有消费分割结果。

而 `script.js` 里唯一能把两者接起来的开关（往 aitype 加 `SKINSEGMENT`）只在 JS 控制器内部生效，
实测全程**没有任何 `open/close FUAITYPE_...` 日志** → 我们的集成路径
（`fuCreateItemFromPackage` + `fuItemSetParamd`）**没走到 bundle 的 JS 控制器**，
所以 `enable_skinseg` 对我们结构性不可用。`delspot` / `nasolabial(v1)` 之所以整帧失效，
也是同一原因：它们是 JS 侧设计，直接写原生参数会让道具进到未正确初始化的状态。

**仍未排除**：`fuRenderItemsMasked` 没试（约半天，签名未知 + 需 GL 上下文）。

**补扫 16–31 位后的定论（同日）**：aitype 的第三个参数是**精确枚举值，不是位掩码**。
1<<0…1<<31 逐位 + 6 组组合全部无效，硬证据在 `ofx.log`：

```
aitype=0x100  预热 859ms  faces=1  sdk=5.0ms   正常
aitype=0x101  预热 313ms  faces=0  sdk=2.2ms   人脸模型根本没加载
```

只要 OR 进任何一位，人脸模型就不加载（预热少掉那 546ms）。所以「加挂皮肤分割」
这个思路从根上不成立，**A1 判死**。

**这类探测必须看 `faces=` 和预热耗时，不能只看像素差异。**

扫描用的 `NAMA_AITYPE_EXTRA` 诊断开关**已撤除**；只保留两样东西：
`fuLoadAIModelFromPackage` 返回值检查（失败时打一条 stderr 警告，以前被静默忽略），

## 两个必须记住的坑

1. **`FUAI_FaceProcessorGetSkinSegResult` 的 `extra` 缓冲实际要 6 个 int。**
   `int extra[4]` 在栈上越界 8 字节，踩坏 /GS cookie → `__fastfail(0xC0000409)`，
   **绕过 VEH 和 SEH**，表现是「第一次 render 整进程静默消失、无 WER 事件」。
   Python 侧 `(c_int*4)()` 在堆上所以看不出来。现在给 256 个 int。
   排查路径：逐调用追踪 → 独立进程复现（正常）→ 模块隔离（仍崩）→ GL 上下文（仍崩）
   → 取原始退出码拿到 `0xC0000409` → 哨兵量出写入量。
2. **掩码全 0 ≠ 掩码不可信。** 那是模型在说「这一帧没有皮肤」，必须什么都不做。
   原来写了个「覆盖度<0.1% 就当没有掩码」的兜底，结果在无脸素材 A7300560 上
   退回全帧磨皮（掩码外 53.94% 被改）。现在改为拿全 0 掩码走合成，整帧不动。
   唯一例外：SDK 检出人脸而 fuai 说没皮肤（判断冲突）才退回颜色启发式。

# 2026-10-26 16:2x 竞品 GT 基准：磨皮拿不到基准，锐化才是差距

## 为什么做

此前所有「我们 vs 第三方」的数字都来自我方离线探针，缺第三方自己的 ground truth。
本轮把这条链路建起来，代价是推翻了一个 P0 判断。

## 链路（可复现，脚本在 `D:\插件\OBS美颜\06_离线验证\gt_基准_20261026\`）

- 第三方参数在 `%APPDATA%\obs-studio\plugin_config\obs-cam-beauty\beauty_profiles\<source_id>.json`。
  **`template` 字段必须指向真实模板文件（如 `e1c09098b433c18ce8a22238fa229888`），
  否则整份 data 被静默忽略**；**参数不热加载，每档必须重启 OBS**。
- OBS 32 虚拟摄像头只支持 Program / Scene 输出（ini 里写 `OutputType=2` 无效）。
- 打破自反馈：让第三方源进 program 场景拿到 `active=True`，再把 sceneItem 位移到
  `positionX=4000` 移出画布 —— 仍在渲染管线里，但不进合成，也就不进虚拟摄像头。
- 抓帧用 `GetSourceScreenshot`（截的是源自身纹理，与画布位置无关）。

## 结果（1280×720；源是 3:4 竖版，有效画面只在 x[369,910]）

| 第三方参数 | 档位 | 细频（3×3 高通） | 与基线平均差 | 最大差 |
|---|---|---|---|---|
| `blur_level` | 0/20/50/80/100 | **100.0%** | 0.0014 级 | ≤2/255 |
| `heavy_blur` | 0/1/2/3 | **100.0%** | 0.01 级 | ≤2/255 |
| `sharpen` | 100 | **555.6%**（中频 441.1%，亮度 −6.5） | 18.75 | — |

校验：① 管线自身噪声（输入原图 vs 参数全 0）平均差 1.25 级 → 磨皮档位差只占 1/874；
② sharpen 100 与基线最佳配准相关 0.9287、偏移 dx=dy=0 → 不是位移伪影。

## 对本项目的三条结论

1. **磨皮「干净度」缺基准，不再当短板计分**。第三方在这条路径上整条磨皮链路不工作
   （它自己 `heavy_blur` 四档也逐字节相同），"我们 85%、它 100%" 无数据支撑。
2. **锐化强度是唯一有 GT 支撑的差距**（555.6% vs 我方 50 档 108%，差一个数量级）。
   这与用户实机反馈"只有第一个磨皮选项有质感、其余只剩锐化"一致。

# 2026-10-26 16:5x v2.0.2：「清晰」独立成增益源（同时把锐化上限放开）

## 起因

竞品 GT 显示锐化是唯一有数据支撑的差距（见上一节）。做标定扫描时先撞到一个真 bug。

## Bug：「清晰」在默认参数下逐字节无效

旧公式（3.0.2 ~ v2.0.1）：

    midGain = (锐化/100) * (kMidGain + 清晰/100 * kMidGainExtra)

「清晰」是中频增益的**乘数**，细频带 amt 也只由锐化算出 ⇒ 锐化 = 0 时两者都是 0，
清晰滑块拖到底输出不变。本地实测（gt_input_720p.png，1280×720，磨皮 50）：

| 参数 | 细频整区 | 中频整区 | 脸框细频 |
|---|---|---|---|
| 磨皮 50（清晰 0） | 98.8% | 98.8% | 95.2% |
| 磨皮 50 + 清晰 100（修复前） | 99.0% | 99.0% | 95.2% |

差异是噪声级 —— 就是"没接线"。而 v2.0 起「锐化」是 `OfxParamPropSecret` 隐藏的，
用户根本没有办法把锐化推起来 ⇒ 面板上那个"实测最强的一项"对所有人都是死的。

## 改法（三个常数 + 调用点一处）

1. `kClarityMid = 2.20`：清晰 100 单独贡献的中频增益（≈ 锐化 67 档的 2.21）。
2. `kClarityFine = 0.50`：清晰也带细频回填，100 → 相当于细频 50 档。
3. `kMidGainMax = 4.40`：中频增益上限从 3.0 放开（原值让锐化 91 档就顶死，
   清晰叠上去完全无效）。默认参数与「全局锐化」那一路（≤3.30）不受影响。
4. 调用点：`midGain = 锐化/100*kMidGain + 清晰/100*kClarityMid`，
   细频 `fineAmt = max(锐化, 清晰*0.5)`，仍以 100 封顶（细频带不放大，见下）。

# 2026-10-26 17:3x v2.1.2：C1 三项美型装机（瘦脸 / 大眼 / 下巴）

## 做了什么

三个**正交维度**的美型项接线：`cheek_thinning`（脸宽）、`eye_enlarging`（眼大小）、
`intensity_chin`（下庭长度）。不接同组的窄脸/V脸/小脸/短脸 —— 它们和瘦脸抢同一块
下半脸像素，同时开会互相打架（第三方只暴露瘦脸、大眼两个滑块就是这个原因）。
参数表 11 → 14 项，面板新增「美型」三项，`face_shape_level` 随之动态 0/1。

## 真正的工作量不在接线，在两遍渲染

美型是几何形变，磨皮是像素级混合，两者不能同帧一遍做：

1. **混合会稀释形变**：`out = t·sdk + (1-t)·src` 逐像素按同一坐标相加，形变
   被 t 稀释并在轮廓留双线（实测磨皮 62 → t 0.62：纯瘦脸 max 165，磨皮+瘦脸只剩 99）。
2. **掩码/贴回基准会错位**：掩码从输入帧算、基准也是输入帧，形变后错位 ⇒
   美白糊到脸外（2.1.0 已修过一次）。
3. **SDK 的 blur_level 是开关不是旋钮**（0 → 98.3%，0.02 就跳到 59.8%，之后
   平坦且非单调）⇒ 不能把强度交给它。

### 2.1.1 的弯路（记下来避免再走）

第一版把形变放第 1 遍、美颜套在形变帧上跑第 2 遍。档位确实连续了，但整体
**偏强 3.5~13.5 个百分点**（磨皮 62：单遍 81.9% vs 两遍 69.7%）。排查结论：
同一个道具一帧渲染两次，第二次的磨皮明显更狠（疑为 SDK 内部时域状态按调用次数
推进），而 blur_level 低端**没有任何梯度**可用于补偿（c_calib_p2b.py 细扫
0.02~0.75 全部钉在 59.8%±0.4），改混合系数 t 又会连带稀释同一遍里的清晰/亮眼/立体。

### 2.1.2 的正确顺序：美颜在前、美型最后

- 美颜遍作用在**原始几何**上 —— 混合两个操作数同几何，与 2.0.x **逐字节一致**；
- 美白/红润/细节回填也仍在原始几何上做（掩码取 src、基准取 src、高频取 src），

# 2026-10-26 20:5x v2.2.0：性能 3.2× + 美型独立成页

两个诉求一起发：**实时预览加了插件从 50fps 掉到 16fps**（性能），以及
**UI 选项太多，把美型隐藏或分割开**（面板整理）。

## 一、性能：热点是锐化，不是磨皮

先用 `perf_breakdown.py`（走 `NamaSelfTest` 的 process/sdk 分段计时）定位，
结论推翻了最初的直觉。

| 阶段 | 1080p | 4K |
|---|---|---|
| SDK GPU 渲染 | 6.9 ms | 18.8 ms |
| CPU 段基线 | 11.6 ms | 30.3 ms |
| +磨皮混合 | +3.5 ms | +14.1 ms |
| +美白 | +0.5 ms | +2.4 ms |
| **+锐化 50** | **+39.1 ms** | **+153 ms** |
| +美型（第二遍 SDK） | +7.9 ms | +20.1 ms |

元凶是 `applySharpen` 的频率分离（横向 3/7-tap + 纵向 7-tap 滑窗 + 逐像素 EMA
时序滤波），4K 下独占 CPU 段的 82%。

**已排除的嫌疑**：fuai 语义掩码 AI 推理。`kRegionEvery=1`（每帧推理）看着可疑，
但它跑在 192×256 低分辨率，单次 2.55 ms，比旧版每 3 帧摊一次（3.82 ms/帧）
还便宜 —— 不是瓶颈。

## 二、做了什么（A+B+C）

| 项 | 内容 |
|---|---|
| **A 并行** | 新增 `RowPool` 持久线程池。`applySharpen` 三阶段、`applyRegionEffects`、`bgraToRgbaBlend` 按行/像素块并行。刻意不用 OpenMP，避免把 libomp 运行时依赖塞进 bundle |
| **B SIMD** | `rgbaToBgra`/`bgraToRgba` 用 AVX2 `_mm256_shuffle_epi8`；`bgraToRgbaBlend` 重写为 AVX2 整数定点 |
| **C 合并** | 新增 `copyRgbaToBgra()`，把 process() 里两处「memcpy + 置换」的两趟扫描合成单趟 |

### 两个必须记住的坑

**① AVX2 混合的 int16 溢出。** 直接照抄标量算式会在两处溢出：
`src*beta + srcT*(256-beta)` 最大 65280（> int16 上限 32767），
`(sdk-src)*t + (srcT-src)*inv` 含负分支、中间量落在 [-65152, 65408]。
解法不是降向量宽度，而是先做代数变形：

```
out = (sdk*t + srcT*inv + 128) >> 8        // t + inv == 256 时与原式恒等
```

变形后三个操作数全非负且 ≤ 65408 < 65535，配 `_mm256_adds_epu16` 永不真饱和。
这段论证已写进代码注释。

**② `col7` 跨行滑窗看似不能并行。** 它是阶段 2/3 的累加器，但真值只依赖当前行
（`Σ_{k=-3..3} tmp7[clamp(y+k)]`），所以每个行块从自己的起始行直接算初值即可，
整数递推精确 —— 这是保证逐字节安全的关键。

### 收益

| 阶段 | 1080p 前→后 | 4K 前→后 |
|---|---|---|
| CPU 基线 | 11.6 → 8.7 ms | 30.3 → 16.9 ms |
| 磨皮混合 | +3.5 → +0.4 ms | +14.1 → +3.5 ms |

# 2026-10-27 00:1x v2.3.0：锐化中间结果不再整帧落地（内存流量优化）

## 起因

用户要「性能优化版」，并明确澄清：**是真正优化性能，不是降画质换速度**。
（中途一度做成「降采样代理档位」，用户否决后已完全回滚，源码不留痕迹。）

## 先被证伪的一条路：继续 SIMD 化

把锐化里最规整、最适合 SIMD 的一段（c7 列累加，纯 int32 加法）改成 AVX2：

| 配置 | 4K 全开 process | 净收益 |
|---|---|---|
| 标量 c7 | 91.0 ms | — |
| AVX2 c7 | 90.4 ms | **0.6 ms（0.7%）** |

**几乎没用。** 归因：锐化 31.4 ms ≈ 300 MB 内存流量（阶段1 读 src 33 MB +
写中间缓冲 100 MB；纵向段再读 100 MB + 写输出 67 MB），300 MB ÷ 10 GB/s ≈ 30 ms，
与实测吻合 ⇒ **瓶颈是内存带宽，不是算力**。带宽打满时加宽车道没用。

## 真正有效的一条：减少内存流量

纵向滑窗在数学上只需要「当前行上下各 3 行」，但原实现把**整帧**的 3-tap /
7-tap 结果写进 `tmp` / `tmp7`（uint16，每像素 12 字节，4K 下 100 MB），
纵向段再整帧读回。

改法（v2.3.0）：

- 取消独立的阶段1，t3 / t7 改由纵向段**按需**计算；
- 每线程一份环形行缓存（t7 8 行、t3 4 行，4K 下各几百 KB）；
- 计算式逐行照抄原实现（同样的整数加法、同样的 clamp 边界）
  ⇒ **输出逐字节不变**；
- `tmp` / `tmp7` 参数保留（不改调用方签名），函数内不再读写。

## 实测收益（两个 DLL 交替测量，取最小值）

| | 4K 全开 process |
|---|---|
| 旧版（整帧缓冲） | 78.6 ms |
| **新版（行缓存）** | **72.9 ms** |
| 净收益 | **−5.7 ms（−7.3%）** |

⚠️ 低于事前「−12~18%」的估计。推测原因：每线程行缓存约 400 KB，未必全部命中
L2；且线程块边界会重复算 7 行（16 线程约 +5% 计算量）。这个偏差说在前面。

## 验证

| 项 | 结果 |
|---|---|
| 逐字节一致性 | v2.1.2 黄金基准 vs v2.3.0 **15/15 md5 全等**（含 3 个美型用例） |
| 19 项回归 | 装机版 **19/19 PASS** |
| 二进制 | `2.3.0` 三处，`2.2.3` 归零 |

产物 md5 `50fea44289937c836dd9e7ae4315d8bf`（编译版 = 装机版）。
旧源码备份 `src/nama_engine.cpp.bak_2_2_3`（回滚用）。

## 遗留 / 下一步

- 行缓存的命中率没实测，若把 `kMinRowsPerThread` 调大（块更大、边界重复更少）
  可能再挤出一点 —— 未验证。
