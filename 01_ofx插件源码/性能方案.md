# DaVinci Beauty —— 性能方案与实测账

> 2026-11-08 建立。目的：把「一核渲染」这件事量化清楚，并记录优化项与验证判据。
> 数据来源：`C:\ProgramData\DaVinciBeauty\logs\ofx.log`（582 帧真机）+ 离线 `NamaSelfTest` 连跑。

## 一、现状（1080p）

| 段 | 真机日志中位 | 离线连跑 | 线程情况 |
|---|---|---|---|
| 掩码 | 0.67 ms（4 帧一次，跑在 worker） | **12.0~13.9 ms（每帧）** | **单线程** |
| 磨皮 | 4.99 ms（GPU） | 3.7~4.5 ms | GPU；上传/读回在单线程串行，读回 5.3 ms 里 5.1 是「等 GPU」 |

CPU 利用率实测（同一帧连跑 6 次，wall vs 进程 CPU）：

| 调用 | wall | CPU | CPU/wall |
|---|---|---|---|
| 1 | 66 ms | 94 ms | 1.4 |
| 2 | 59 ms | 172 ms | 2.9 |
| 3 | 58 ms | 188 ms | **3.2** |

20 核机器，峰值 3.2 核。**根因：掩码是整帧最大的单线程块**（占一半以上），其余段早就并行了但都很小。

另：4.5% 的帧 >50 ms、最高 235 ms，全是**首帧**（着色器编译 + 纹理首次落物理页），会卡在片头。

## 二、优化项

### ① 掩码绘制并行（已开工，1.2.6）
`buildMaskInto` 的脸框绘制是逐行独立的，只往自己那一行写 `mask_`；共享的只有统计量
（`px` / 包围盒）。做法：统计量改成「每块局部累加 + 末尾合并」，套现有的
`parallelRows` 持久线程池。

- 范围：**只并行脸框的矩形/椭圆两支**。脖子带不参与 —— 它读的 `colEnd` 是
  `thread_local` 的、由调用线程上一趟算好，换线程会读到空表。
- 线程数：`g_cfg.threads`（Resolve 里 = 物理核−1，本机 11），上限 16，且每线程至少 32 行。
- **验证判据：掩码必须逐字节不变**。参考帧 5 张（夹具 g_005/g_010/g_015/g_020 + 真机 dump_re）：
  ```
  ref_g_005   148f4dab662018f74faae41dfdcbb46f
  ref_g_010   87d0db73ca783f285d3265dd2932d1b3
  ref_g_015   e2b1f10b088e5ebb9935e661aa00058a
  ref_g_020   19a85c9dfb647c24e684ae3e3525b531
  ref_resolve ad330857b4079d4510f2d18ed7dd6b7e
  ```
- 预期：掩码 13 ms → 3~4 ms；整帧 24 → 14 ms；CPU/wall 3.2 → 6~8。

### ② GPU 停等改流水
`读回=5.3(等GPU 5.1)`：提交完就阻塞等。延迟取回管线已有（`gpu_smooth_pipeline`），
导出时常因「画面在动」退回同步。导出模式下帧是顺序来的，可强制「本帧提交、下一帧取回」。
预期 5 ms → 2~3 ms。

### ③ 掩码节流
`kMaskEverySync` 现在 4 帧。导出时按「人脸框位移 < 2 px 就沿用」延到 6~8 帧。
预期均值 13 → 6.5 ms，零代码风险。

### ④ 掩码降分辨率（不推荐先做）
1/2 分辨率算再上采样，13 → 3 ms，但边界会糊 —— 1.1.3~1.1.7 九版都在治边界，不要动。

## 四、已完成（1.2.6 / 1.2.7，2026-11-08）

### 1.2.6 掩码绘制并行
- `buildMaskInto` 的脸框矩形/椭圆两支改成按行并行（`parallelRows` 持久池），
  统计量 `px`/包围盒改成「每块局部累加 + 末尾合并」；脖子带保持串行
  （它读的 `colEnd` 是 thread_local，换线程会读空表）。
- **验证：5 张参考帧 mask md5 全部逐字节一致**，`baseline.py check` 18/18 PASS。
- 收益：同步路径掩码 13.9 → 11.1 ms。

### 1.2.7 推理线程可调
- 新增 `BEAUTY_INFER_THREADS`（1..16），默认仍是 2 —— 直播场景编码占 4~6 核，不能抢。
- 实测（1080p，同一帧）：2 → 掩码 11.85 ms；4 → 10.53；8 → 9.84。

### 归因修正（重要）
原以为掩码 11 ms 里「绘制」是大头，实测**不是**：

| 关掉什么 | 掩码 |
|---|---|
| 默认 | 11.15 ms |
| 脖子带关（`BEAUTY_NECK_LEN=0`） | 9.69 ms（带只占 1.5） |
| 推理线程 2 → 8 | 11.85 → 9.84（检测约 2 ms） |
| 绘制并行前后 | 13.9 → 11.1（绘制约 2~3） |

加起来只有 ~5 ms，**剩下 ~7 ms 是固定开销**（`memset` 两张全帧缓冲 ≈ 4 MB、
五官保护椭圆、掩码搬运等）。继续优化前必须**先在 `buildMaskInto` 内部打点**，
不要再靠推测切分 —— 这条是本轮最大的教训。

## 六、1.2.8 打点结果（谜团解开）

`BEAUTY_MASK_PROFILE=1`，1080p 真机帧：

```
掩码分解 检测=6.75 memset=0.14 肤色=0.18 脸框+脖=2.67 保护=0.00 合计=9.73
```

- **ONNX 人脸检测 6.75 ms** —— 占掩码的 2/3，此前完全没被单独量到（它和画掩码一起
  包在「掩码」那一段里，所以怎么改绘制都只动 2~3 ms）。
- `memset` 两张全帧缓冲只有 0.14 ms —— 之前"4 MB memset 很贵"的猜测是错的。
- 「脸框+脖」2.67 ms（1.2.7 并行前约 4.5）。

⇒ 掩码这条线的下一步只有三选一（按性价比）：

| 手段 | 预期 | 代价 |
|---|---|---|
| `BEAUTY_INFER_THREADS=6~8`（导出） | 检测 6.75 → 5~6 | 多占 4~6 核，直播别开 |
| 检测降到每 4 帧（复用上一帧人脸框，位移超阈值才重测） | 均值 6.75 → 1.7 | 极快甩头时框会滞后 1~2 帧 |
| 检测输入边长 640 → 480 | 检测 ×0.6 | 侧脸/小脸召回略降，需要真机核 |

我建议先做第 2 条（复用 + 位移判据），它不动算法精度，且导出时人像移动慢，命中率高。

## 七、1.2.9 检测复用（已落地）

判据：64×36 灰度缩略图的平均绝对差 ≤ `g_detThr`（默认 2.0 级）且距上次真检测
不超过 `g_detAge`（默认 4 次重算）时就沿用上一帧的人脸框。回退：`BEAUTY_DET_REUSE=0`。

24fps 连续 11 帧实测（1080p）：

| | 复用帧（8/11） | 重测帧（3/11） | 平均 |
|---|---|---|---|
| 检测 | **0.03 ms** | 6.5~7.7 ms | 1.9 ms |
| 掩码合计 | 2.7~2.9 ms | 9.4~10.5 ms | **4.7 ms** |

对比全检测：掩码平均 9.8 ms → 4.7 ms（**−52%**）。

质量代价（同一序列，复用 vs 全检测的掩码逐字节比）：

```
frame0: 0.000    frame1: 0.300    frame2: 0.000
frame3: 0.179    frame4: 0.260    frame5: 0.000
（mean|Δ|/255；差异集中在羽化带，≤1% 像素差 >8）
```

即边界滞后约 1 帧。静止/慢速镜头零差异；快甩头由 `detAge=4` 兜底重测。

**注意**：单帧用例（18 个基线、5 张参考帧）永远走"首帧必检测"，所以基线逐字节不变，
这条优化的效果只能在**序列**上量到——这也是它容易被误判为"没生效"的原因。

## 八、1.3.1 色调权重低通并行（已完成）

`toneColor` 里那两遍盒式均值（R=24 长斜坡 + R=3 门控）原本是串行的，占了色调段
4.1 ms 的一半以上。现在 H 遍按行切、V 遍按列切，走 `parallelRows`。

- 实测整帧 wall **60.8 → 57.0 ms**（−3.8，含自测路径 ~35 ms 的文件 I/O 噪声）。
- **逐字节不变**：18/18 基线、5 张参考帧 mask 全 IDENTICAL。

**踩到的坑（已写进代码注释）**：`wbuf/wtmp` 是 `thread_local`。并行前必须在
**调用线程**取好裸指针再传进去；否则工作线程拿到的是各自那份**未 resize** 的
vector，写越界直接 0xC0000005。第一版就是这么崩的。

## 九、试过但回退的：ROI 对齐 32 像素

延迟取回管线要求「输出矩形一帧内不变」，真机 327 帧里 109 帧因为包围盒抖 1~3 px
退回同步（白等 4~5 ms）。把 ROI 向外对齐到 32 的倍数能让矩形基本恒定 —— 但实测
**14/18 基线会变**（半分辨率平面的采样相位跟着 ROI 起点走），所以回退了。
要做这条，得先把平面原点的相位固定成与 ROI 无关，那是 GPU 路径内部的改动。

## 十、还剩什么

- 磨皮读回里 **89% 是「等 GPU」**（中位），算只占 0.5 ms —— 延迟取回只能在
  「画面静止」时生效（`stillOk` 判据），跳舞镜头基本不会命中，这条短期无解；
- 掩码平均 4.7 ms（重测帧 9~10），检测复用已吃掉大头；
- 首帧 235 ms 预热（着色器编译 + 纹理落实物理页）仍未挪走。

## 十一、1.3.2：5.66 ms 劈开了 —— 执行 4.53 / 拷贝 0.11

加了 `D3D11_QUERY_EVENT`（`BEAUTY_GPU_PROFILE=1` 时每帧一行）：

```
GPU 提交分解 执行=4.53 拷贝+回读=0.11
```

结论很干脆：**等待全在 GPU 执行，拷贝可以忽略**。

| 假设 | 实测 | 判定 |
|---|---|---|
| 提交/Flush 慢 | 算=0.50 ms（含 Flush） | ✗ |
| staging 拷贝大（4.5 MB BGRA） | 拷贝+回读 = 0.11 ms | ✗ |
| dispatch 链执行慢 | **执行 = 4.53 ms** | ✓ |

10 次 dispatch（DOWN → BOXH/BOXV×3 → AMP → BOXH/BOXV×3 → COMPOSE）跑在
512×540 的平面上只要 ~2.8M 像素操作，4.53 ms 说明**瓶颈是 dispatch 次数与状态
切换，不是像素量**。

### 下一步的做法（方向已定）

1. **BOXH+BOXV 合成一趟 2D 盒式**：3 趟 → 3 次 dispatch 变 3 次（但省掉中间 plane 的
   读写与绑定），或直接用一次 group-shared 的 2D 卷积；
2. **AMP 的 3 趟盒式**同理；
3. **COMPOSE 与最后一趟 BOX 融合**（最后一趟写 UAV 的同时做合成，省一次全分辨率 dispatch）；
4. 目标：10 → 4 次 dispatch。

注意：合并 pass 会改变浮点累加顺序，**输出不会逐字节相等**，需要逐用例核 ±1 级
并重标基线。这条要用户点头才动。

## 十二、BOXH+BOXV 合并（6→3）的设计定稿，待实施

现状（`CSBoxH` / `CSBoxV`）：H 一遍是「一个线程算 32 个连续像素，每 32 像素从头
重算窗口和」；V 一遍是「一个线程算一列 32 行，每 32 行重算」。两遍各 3 趟 = 6 次 dispatch。

合并方案（一个 group 吃一个 32×32 的输出块）：

1. 线程组 32×8（256 线程），groupshared 存 **44×32 的 float4**（32+2r，r≤6 → 44）≈ 5.6 KB，远低于 32 KB；
2. **阶段 A（H）**：每线程负责 44 行里的 5~6 行，对每行算 32 个 H 值写进 groupshared。
   列方向带 ±r 的 halo（越界 clamp），flush 语义保持「每 32 像素重算一次」，
   与 CPU 的 `x & 31 == 0` 对齐，所以结果与现在两趟完全一致（只差浮点累加顺序）；
3. **阶段 B（V）**：每线程负责 4 个输出列，从 groupshared 里对 32 行做窗口和，
   行 halo 用步骤 2 多算的那 ±r 行；flush 在 `y & 31 == 0`，与 CPU 一致；
4. 3 趟就变成 3 次 dispatch（而不是 6 次），预计省 ~1.3~1.5 ms（每次 dispatch 约 0.45 ms）。

**为什么值得这么做**：1.3.2 已证 执行=4.53 / 拷贝=0.11，瓶颈是 dispatch 次数与状态切换，
不是像素量或带宽。

**风险与验证**：
- 浮点累加顺序变了 → 输出**不会逐字节相等**，必须逐用例核 ±1 级并重标基线；
- 建议先只替换 `runBox`（磨皮的主路径），用 `BEAUTY_GPU_BOX2D=0/1` 做 A/B，
  两边输出逐像素比，超过 ±1 级的像素数必须为 0 才允许切换默认值；
- 如果 groupshared 版本在 4K 上因占用率下降反而变慢，保留旧路径不删。

## 十三、BOX2D 合并实测：**假设被证伪**

按第十二节写了 `CSBox2D`（32×32 一个 group，groupshared 存 44×32 的 H 结果，
V 用滑动窗），`BEAUTY_GPU_BOX2D=1` 开关，默认关。

| 版本 | 执行 | A/B 输出 |
|---|---|---|
| 每线程 4 行、每点 13 个 tap（第一版） | **5.97 ms**（比旧路径 4.46 慢） | mean Δ=0.000，max 2 级，3 px |
| 改成滑动窗（每点 +2 次 shared 读） | **5.65 ms**（与旧路径 5.89 持平） | mean Δ=0.000，max 3 级，1 px |

结论：

1. **数值是对的** —— 两版都与两次 dispatch 的结果一致（最大差 2~3 级、个位数像素），
   说明 flush 语义对齐没有问题；
2. **性能没有收益** —— 6 次 dispatch 合成 3 次，执行时间不变。所以
   「4.53 ms 是 dispatch 开销」这个推断**是错的**；
3. 真正的成本是 **tap 数 × 像素数 × 趟数**：512×540 平面 × 13 taps × 3 趟 × 3 个通道
   ≈ 3200 万次乘加 —— GPU 在老老实实算，不是排队。

### 那还能怎么降？

只有降低「每像素的工作量」，三条都能砍一半以上，但**都会改变输出**：

| 手段 | 预期 | 代价 |
|---|---|---|
| 趟数 3 → 2（盒式³ → 盒式²） | −33% | 模糊核形状变了，观感偏"方" |
| 半径不变、平面降到 1/3 分辨率 | −55% | 细节丢失，边界更糊 |
| 用可分离的**高斯近似**（一次 H、一次 V，核更宽） | −50% | 与参考实现不再逐像素对齐 |

**建议**：这条线到此为止。GPU 已经是"算得动但在真算"的状态，再往下都是拿画质换时间，
而画质正是前面九版在救的东西。
