# DaVinci Beauty OFX —— DaVinci Resolve 美颜滤镜（v3.0.8）

一个给 DaVinci Resolve Studio 21.1 用的 OpenFX 滤镜，效果引擎是 OBS 美颜 3.1.39 自研的
纯 CPU 美颜引擎（CoreEngine），人脸检测用 ONNX YuNet，并在引擎内部**自动检测 GPU**
（仅 Windows DirectML）：把 onnxruntime.dll 换成 onnxruntime-directml 构建版，人脸推理
就自动走 GPU，否则自动退回 CPU。装上以后它就是一个普通滤镜：拖到片段上，拖滑块，
检视器实时刷新。v3.0.0 起彻底脱离闭源 FaceUnity NamaSDK。

这是本项目当前的主交付形态。早期做的「工作区 → 脚本」Lua 版已移出脚本菜单
（代码保留在 `C:\ProgramData\DaVinciBeauty\disabled_scripts\`），两条路线不再并存。

## v3.0.8 变更（2026-10-31，工程验收 + 性能优化，画面逐字节不变）

18 个逐字节黄金用例的 md5 与 v3.0.7 完全一致 —— 本版**不改任何画面算法**，
只改「能不能稳定构建 / 装机判据 / 每帧内存搬运 / 测试覆盖 / 死代码」。

**（1）构建链路：.bat → PowerShell。** 旧 `build.bat` 把 `..\02_引擎资产\onnxruntime\include`
以 GBK 字节写死，而 cmd 按当前代码页解析批处理：控制台切到 65001 后中文路径变乱码，
cl 直接报 `cannot open include file: onnxruntime_c_api.h`（本次验收第一次构建就复现）。
`%~dp0` 这类动态展开没事，**出问题的永远是批处理里的中文字面量**。
现在 `build.bat` 只是 `build.ps1` 的薄壳：vswhere 探测 VS → 取最新 MSVC 与 Windows SDK →
`src\*.cpp` 全量编译。中文路径与 argv 都走 UTF-16，不受代码页影响；`build.ps1` 自身
是**纯 ASCII**，任何代码页下都能解析。顺带支持 `-Clean` / `-NoInstall`。

**（2）装机判据：从「是否管理员」改成「能否创建目录」。** `install.bat` 原来用
`net session` 判权限：受限的管理员令牌（UAC 未提升、但目标目录 ACL 已放行）会被误判成
「不是管理员」；反过来，提升的 shell 也可能被组策略拒绝写 Program Files。
现在只在 `mkdir "%TARGET%"` 失败时报错 —— 创建目录才是唯一诚实的判据。

**（3）8bit 直通路径：省掉两次全帧拷贝。** 宿主给 8bit、行无填充、输入输出 bounds 一致时
（Resolve 常规路径），旧代码是「源图 → 线程缓冲 → 引擎 → 线程缓冲 → 目标图」，
两次 8.3MB/帧的搬运纯属多余。现在引擎直接读源图、写目标图（`src`/`dst` 是宿主给的
两张不同图像，引擎对 `src` 只读 —— 见 `beauty_core.h` 的 `process()` 契约）。
1080p A/B 交替 5 轮取最小值：**24.5 → 20.5 ms/帧**。float、bounds 不一致、有行填充的
路径保持原样；float 输出的逐像素统计（改动≥3 的像素 8287、残留哨兵 203）与旧版一致。

**（4）测试覆盖：14 个滑块逐个独奏。** `baseline.py` 只覆盖 6 个参数，「立体 / 亮眼 /
去眼袋 / 去法令纹 / 祛斑 / 红润」六项从未单独测过。`mock_host.py` 新增一轮：每项单独
拉到 100、其余归零，用**改动像素占比**判「有没有接线」而不是 MAD —— 去眼袋满量程只改
0.33% 像素、MAD 0.0065，用 MAD 判会误报成没接线。结果 14/14 全部改动画面（最大 60.7%
全局锐化，最小 0.20% 亮眼），无空接线。

**（5）可复现构建：`/Brepro`。** 链接加 `/Brepro` 后，同一份源码重复编译得到**逐字节相同**的
DLL（此前 MSVC 会写 PE 时间戳，每次重编 md5 都变，「装机 == 编译产物」只能做行为等价，
文档里的 md5 也永远过期）。本次连续两次 `build.ps1` 的 md5 都是
`40df78a2dc7bce61ed6f8f5e027114fe`，acceptance 的字节判据从此是硬判据。

**（6）清死代码 + 两处 UB 苗头。** 删掉 v2.x NamaSDK 遗留的 GL 隐藏窗口、SDK 道具池
`Slot`（60 行结构体 + 注释）、渲染临时缓冲、区域映射表等 20 个成员，以及 7 个只有声明
没有定义的方法。另修：`faceScore_` 是 `float` 却接收 `double`（C4244 告警，改 double）；
`version()` 返回可变函数静态 `std::string` 的 `c_str()`，而调用方写的是
`version() ? version() : "?"` —— 两次调用之间若重新赋值，第一个指针就可能悬空。
现在只在内容变化时改写，指针在引擎就绪后保持稳定。

验收：`mock_host.py` **23/23**、逐字节 **18/18**、`acceptance.py` **25 PASS / 0 FAIL / 0 WARN**。

## v3.0.7 变更（2026-10-31，加强磨皮强度 + 放大四组档位差异）

用户实测反馈：**「磨皮算法三档 / 磨皮模式四档，无明显变化」**。上一版已确认参数确实送到
引擎（真机 `ofx.log` 里 `blurType` 0/1/2、`smoothMode` 0–3 全都出现过），所以问题不在接线，
而在**幅度**。真机帧 1080×1920、面板磨皮 100 的量化结果：人脸区与源帧的平均绝对差只有
**0.955 灰阶**、峰值 13 灰阶、改动 >3 的像素仅 14.2%。

**（1）磨皮本身加「强度总增益」。** 新增 `beautycore::amplifySmooth()`：

```
dst' = src + (dst − src) · gain        // gain = 1 时逐字节等于 v3.0.6
```

为什么不用「让 I 突破 1」：surface3 的合成式就是 `res = c + (even−c)·I`，`I>1` 与事后乘 gain
数学等价，但**只有 surface3 这一条路有 I**；高斯档、legacy 盒式、25 tap、降采样四条老路径
强度各有各的腿（有的压根没有 I）。事后统一乘一次就都管住了，而且不动 `lvI`/`lvE` 的标定
（那是按产品五档强度占比 0.005/0.211/0.588/1.0 反解的，改表就毁掉标定）。

定档扫描（`src.raw`，只开磨皮 100，人脸区 400–780 × 330–710）：

| gain | res | maxd | p>3% | tex（高频保留率） |
|---|---|---|---|---|
| 1.00 | 1.014 | 13 | 16.2% | 0.942 ← v3.0.6 |
| 1.60 | 1.619 | 21 | 27.5% | 0.950 |
| **1.80** | **1.82** | **23** | **~30%** | **~0.953** ← 取这里 |
| 2.00 | 1.976 | 26 | 34.2% | 0.957 |
| 2.40 | 2.334 | 31 | 35.5% | 0.998 ← 纹理回涨，开始「加噪」 |

卡在 1.8 而不是 2.4：`res` 虽然还在涨，但 `tex` 从 0.957 跳回 0.998 —— 那不是「磨得更狠」，
是 `(dst−src)` 里的**振幅门控结构**被一起放大到压过了磨皮本身，观感变成「平了但发毛」。
现场可调：`BEAUTY_SMOOTH_GAIN`（0.25–3.0）。

**（2）混合类路径不许外推。** 高斯 / legacy 盒式的强度就是混合权重 `tBlend`，`tBlend>1` 的
语义是「比完全平滑还平滑」，落到模糊图上等于反向补偿边缘 → 硬边 + 光晕（实测外推到 1.51 时
人脸区最大改动 87 灰阶）。所以这几条路只把增益乘进 `tBlend` 并**封顶 1.0**，`amplifySmooth`
只给 surface3 的重建路径用。封顶后高斯档最大改动 87 → 59。

**（3）四组档位差异全部放大。**

| 档位 | v3.0.6 | v3.0.7 |
|---|---|---|
| 1 高斯 | 只去保边（r=2 的 5×5 近盒平均，等效 σ≈1.4px） | **半径 ×2**（9×9，σ≈2.6px） |
| 2 弱磨皮 | `I × 0.5` | `I × 0.30` |
| 1 清晰 | `fine×2.2 + mid 0.18·I` | `fine×4.0 + mid 0.45·I` |
| 2 精细 | `fine×3.2 + mid 0.40·I` | `fine×5.5 + mid 0.75·I` |
| 3 轻磨皮 | `I × 0.55`（高斯档 `t×0.55`） | `I × 0.40`（高斯档 `t×0.40`） |

真机帧复测（用户真实参数 磨皮100/清晰31/美白67/大眼9/下巴19，人脸区与源帧平均差）：

| 对比 | v3.0.6 | v3.0.7 |
|---|---|---|
| 高斯 vs 双边 | 1.007 | **1.467**（max 87 → 59） |
| 弱磨皮 vs 双边 | 0.492 | **1.159** |

**（4）夹具断言改口径。** `mock_host.py` 原来判「精细 = 离源帧更远」，那在回填增益提到 5.5
之后必然失败 —— 而画面完全正确（**回填越多越接近原图**，距源帧本就该变小）。改为在「磨皮
脚印」内量 **9×9 中频高通**保留率（`|G − box9(G)|`）：人像 8.397 < 清晰 8.781 < 精细 9.069，
方向单调；「轻磨皮」仍用距源帧判（它的语义就是降强度）。3×3 细频不够用 —— 回填主体是中频，
细频只有 `0.06·I·4.0`，四档之间只差 0.5%，断言拉不开。

版本号 `3.0.6 → 3.0.7`（修订位 +1）。测试：`mock_host.py` **20/20**、逐字节基线 **18/18**

## v3.0.6 变更（2026-10-31，两个下拉框的**面板侧**缺陷）

v3.0.5 把「磨皮算法」三档与「磨皮模式」四档在引擎里接上了，但**真机拖下拉框仍然不对**。

`NAMA_ST_ALG` / `NAMA_ST_SMOOTH` 钩子，**绕过了这一层**，所以 18/18 全绿也发现不了。

| 缺陷 | 现象 | 原因 |

## v3.0.5 变更（2026-10-31，美形三项的 y 方向 + 两个下拉框接线）

用户在 Resolve 里实测：「除了大眼正常，瘦脸和下巴的功能不对。位置不对。模式和算法也不对。」

**(1) 瘦脸 / 下巴的 y 方向反了。** `beauty_warp.cpp::makeGeom()` 里 `chinY = f.y + f.h`、
`eyeY = f.y + 0.38h`、`mouthY = f.y + 0.72h` 全按 top-down 写，但 v3.0.4 之后 `f.y` 是**缓冲行号**
（bottom-up 下它是脸框的视觉下沿）→ 下巴底取到发际线、嘴线取到额头，嘴线合理性校验
`my > eyeY+0.05h && my < chinY` 恒假（嘴角缓冲行号比眼小），关键点嘴线被丢弃。
于是瘦脸的高斯中心跑到眉毛、下巴压的是头发。**大眼是径向各向同性且眼心来自关键点，
所以只有它正常** —— 这正是用户看到的现象。

修法：`warpFace()` 加 `bool flipY`，`sgn = flipY ? -1 : +1`，比例值换成从缓冲最小行往上数
（`0.38→0.62`、`0.72→0.28`），嘴线校验与下巴不等式统一乘 `sgn`。
真机帧（1080×1920 bottom-up）离线复验：眼 457 < 瘦脸 511 < 下巴 615（视觉坐标）全部通过，
`shape100` 用例 md5 与 v3.0.4 一致（`flipY=false` 路径零变化）。

**(2) 「磨皮算法」「磨皮模式」真正接线。** 此前两者只是被塞进 `BeautySettings`，`process()`
从不读取（基线里 `mode1/2/3` 与 `blur62_wh30` 同 md5 即为证据）。默认档保持逐字节不变：

| 磨皮算法 | 实现 |
|---|---|
| 0 双边滤波（默认） | 现状 `surface3Rgb` 保边路径，逐字节不变 |
| 1 高斯 | `bilateralRgbaRoi` + `sigmaColor=255` → 退化成纯空间高斯，边缘一起糊 |
| 2 弱磨皮 | 同一套 `surface3Rgb`，`I *= 0.5` |

| 磨皮模式 | 实现 |
|---|---|
| 0 人像（默认） | 不回填，逐字节不变 |
| 1 清晰 | 基准回填 `fine×2.2` + `mid 0.18·I` |
| 2 精细 | `fine×3.2` + `mid 0.40·I` |
| 3 轻磨皮 | 不回填，`I *= 0.55` |

基线从 15 条扩到 18 条（新增 `alg0/alg1/alg2`），原有 15 条 md5 **全部不变**。
详见 `开发文档.md` §6-c、`开发指南.md` 约束⑧。版本号 `3.0.4 → 3.0.5`（修订位 +1）。

## v3.0.4 变更（2026-10-31，帧行序 bottom-up —— Resolve 侧 faces=0 的真因）

v3.0.3 修完三个「假故障」后，Resolve 里 `sdk` 耗时已正常（≥15ms，检测真跑了），但仍是
`faces=0 score=0.25`。把真机帧原样 dump 出来离线复跑，定位到**帧行序**：

| 读行方向 | bestScore | faces |
|---|---|---|
| top-down（v3.0.3 及以前） | **0.2519** | 0 |
| bottom-up（v3.0.4） | **0.9333** | **1** |

**OFX 规范规定 `kOfxImagePropData` 指向图像左下角**，Resolve 严格照做（第 0 行是画面最下面一行）；
而 PIL/numpy 与所有离线夹具都按 top-down 存帧 → 「离线 0.92 通过、真机 0.25 全灭」。

实现：`letterboxRgb()` 本就要缩放重采样，读行直接换成 `sh-1-y`（零成本，不整帧翻转）；
检测出的框/关键点是视觉坐标，再映射回缓冲行号（`f.y = h - vy - f.h`、`kps.y = h - vy`），
掩码/磨皮/美白/几何变形全按缓冲行号落笔，下游一行不改。引擎默认 `imgBottomUp_ = true`。

配套：`mock_host.py` 新增 `_to_bottom_up()`（夹具帧序与真机一致，此前夹具替插件掩盖了方向 bug）；
`NamaSelfTest` 恢复 `NAMA_ST_*` 钩子并强制关异步（此前 8 个基线用例实际只覆盖 4 种参数、且不可复现）；
`baseline_manifest.txt` 按新引擎重新标定。详见 `开发文档.md` §2-c。版本号 `3.0.3 → 3.0.4`（修订位 +1）。

## v3.0.3 变更（2026-10-31，修掉三个「假故障」）

「清晰正脸、画面毫无效果、日志 `faces=0 score=0.00`」的真因不是检测算法，而是三处工程问题：

1. **离线自测夹具喂错数据**：`NamaSelfTest` 把「文件路径」当成「图像数据」直接送进检测（喂进去的是字符串 `C:\Users\...`），**v3.0.1/v3.0.2 期间所有离线「0 检出」结论全部作废**。修复后同一张图 `faces=1 best=0.9214`，与 Python 参考值完全一致。
2. **异步检测在按需渲染宿主里永久透传**：Resolve 只在播放头移动时渲染，worker 结果赶不回来 → 永远走「首帧透传」。改为**首帧先同步检测一次**。
3. **参数句柄失败静默给 0**：面板全 0 → 引擎逐字节透传（日志 `sdk≈1ms`）。改为回落声明默认值 + 打 WARN。

新增 `面板参数` 变更日志、`BEAUTY_DEBUG_DETECT`、`BEAUTY_DEBUG_DUMP` 三个诊断手段。详见 `开发文档.md` §2-b。版本号 `3.0.2 → 3.0.3`（修订位 +1）。

**架构级变更：移除闭源 FaceUnity NamaSDK，引擎层整体替换为 OBS 美颜 3.1.39 的自研
纯 CPU 美颜引擎（CoreEngine），人脸检测用 ONNX YuNet。**

## v2.0.1 变更（2026-10-26，Resolve 内实测后修复）

来自装机后逐项试用的四条反馈：三处真缺陷，一处命名与行为相反。

### 1. 日志从来没有写出来过（修）

`ofxLog()` 用 `CreateDirectoryA` 只建**一级**目录。装机后 `C:\ProgramData\DaVinciBeauty`
本身不存在，于是 `...\logs` 建不出来、`fopen` 失败、每条日志被静默丢弃 ——
插件在 Resolve 里跑多久都不会产生 ofx.log，这段时间「出错就看日志」的排查其实都是空的。
旧代码还有 `static bool dirOk` 无条件置位，第一次失败就永久放弃重试。

现在按分隔符逐段创建，只有确认目录真的存在后才缓存。
实测：删掉整个 `C:\ProgramData\DaVinciBeauty` 后跑一次，日志自动重建。

### 2. 磨皮四档实际是「磨皮 + 50 档锐化」（修，本次最重要）

用户原话「只有第一个选项达到快速磨皮且保留质感，其余只有锐化的效果」，
在代码里能一字不差地找到原因。

`texModeNeedsBaseline` 给模式 1/2/3 一个「基准回填」，基准取「锐化 50」。
而 faceAmt 同时驱动两件事：细频带 alpha，以及

    midGain = (faceAmt/100) * kMidGain = 0.5 * 3.30 = 1.65

按 `kMidGain` 自己的标定注释，锐化 50 就是把 3~7px 中频带推到原图的 **149.8%** ——
那正是「锐化」的定义。模式 0 不带基准回填、根本不走这条路径，才是纯 SDK 磨皮。

修法：基准回填**只给细频带**，中频增益只在用户显式动了「锐化」或「清晰」时才给。

实测（640×394 人像帧，磨皮 50，相对原图的高频能量）：

| 选项 | 细频·平坦区 | 细频·边缘区 | 中频 3~7px |
|---|---|---|---|
| 0 人像磨皮 | 92.3% | 100.2% | 98.8% |
| 1 清晰磨皮 | 94.3% | 107.1% | 101.0% |
| 2 精细磨皮 | 96.8% | 104.2% | 100.1% |
| 3 轻磨皮 | 96.7% | 101.5% | 99.2% |
| 对照：真正的锐化 50 | 105.6% | 106.5% | 108.2% |
| 对照：真正的锐化 100 | 116.3% | 111.9% | 116.3% |

四档全部低于 100%（都是磨皮），锐化 50 才把它推到 100% 以上。

### 3. 「朦胧磨皮」名不副实（改名）

`kTexModes[3] = {140,0,0}` 的语义是「按面板档位的 55% 回填细频」，是**正回填**。
本引擎没有负回填（hf 取自原图，减它会把边缘挖穿），所以它做不到「比纯磨皮更糊」。
实测它是四档里细节留得最多的一档，故改名 **「轻磨皮（细节保留最多）」**。
四档文案同步按实测排序：人像（SDK 原始质感）/ 清晰（轮廓最立体）/
精细（轮廓小幅增强）/ 轻磨皮（细节保留最多）。

### 4. 输入像素编码自检（新增）

引擎把输入一律当非线性编码像素处理（`f32_to_u8_row` 是纯 `v*255`）。这在下述配置下
正确：色彩科学 DaVinci YRGB（非 Color Managed）+ 时间线 Rec.709 (Scene) ——
送入的就是 Rec.709 编码值。

但换到 Color Managed / ACES 项目时宿主可能改送 scene-linear，那时 18% 灰会被映射成
46/255 而不是 105/255：画面压暗、人脸漏检、美白比例失真，**且不报错**。

现在每个实例在首帧采一次亮度分布写进日志：

    inputProbe 中位=123/255 黑1%=0 亮99%=231（非线性编码，正常范围）

中位 < 55 就记 WARN（已排除纯黑遮幅，否则黑边会让中位恒为 0）。
**不做自动补偿** —— 补偿需要确切的传递函数，猜错比不补偿更糟。

### 4K 耗时实测（首次有实测值）

| 分辨率 | 像素数 | process | 等效帧率 |
|---|---|---|---|
| 1080p | 2.07 M | 69.7 ms | 14.3 fps |
| 4K UHD | 8.29 M | 167.5 ms | 6.0 fps |
| 4K DCI | 8.85 M | 180.7 ms | 5.5 fps |

数字来自 C ABI 自测路径（直接调 `NamaEngine::process`，绕开 OFX 与宿主），
每档 3 次取中位。比 OBS 侧线性拟合外推的 226 ms 好一些，但 **4K 实时预览仍然跑不动**，
需要开 Render Cache 或降预览分辨率。

## 为什么是回移而不是重做（决策记录）

两条代码线是同一份引擎的两个宿主壳：v1.51 的引擎曾移植进 OBS，OBS 那条线随后
独立迭代了 3.0.x 共十九个版本，现在把成果回移回来。

| 证据 | 数值 |
|---|---|
| `nama_engine.cpp` 逐行相同 | 1,296 / 2,316 行（56%） |
| `nama_region.cpp` 逐行相同 | 417 / 973 行（43%） |
| 宿主层工作量 | OFX 协议层 1,237 行、19 项无宿主回归、打包器、装机脚本，v1.51 全部做完 |
| 从零重做的代价 | 重复踩 v1.51 已文档化的 9 个坑（时间透传致画面定格、代理帧白跑 17.7ms、GetClipPreferences、多实例串扰、通道序 BGRA 等） |

回移后必须重新标定的两项，原因都是**曲线模型变了**，不是回移出错：

1. **磨皮**：v1.51 的滑块 10 档就接近饱和（实测 mad 10 档 0.167、100 档 0.207，只差
   1.24 倍），OBS 3.0.8 改成了「SDK 满强度 + CPU 线性混合」，所以同名的 20 档在 v2.0
   里只有 v1.51 的约 1/5 强度。处理办法是把默认值提上去（v2.0 提到 50，
   v2.0.3 按竞品 GT 插值提到 62），文档写明换算。
2. **美白**：OBS 3.0.18 以第三方商业美颜为锚点（55 档 +5.66、满档约 +10）反解出
   kMax=0.16；v1.51 的 0.40 对应满档 +25，比商业产品强约 2.5 倍。v2.0 采用 0.16。

两项都属可回退决策：想回到 v1.51 的强度，改 `applyRegionEffects` 的 kMax 与
`kParams` 的默认值即可，不需要动架构。

### 什么时候要重启 Resolve

Resolve 把扫描结果缓存在
`%APPDATA%\Blackmagic Design\DaVinci Resolve\Support\OFXPluginCacheV2.xml`，
缓存以 `mtime + size` 判断是否失效：

- **重新编译过插件** → 二进制指纹变了 → **必须重启 Resolve** 才会重新扫描。
- **只是重启 Resolve、没改过插件** → 走缓存，不需要额外操作。

想确认 Resolve 认没认，直接看那个 xml 里有没有 `com.nama.davinci.beauty`，
并核对 `mtime` / `size` 与磁盘上的 `DaVinciBeauty.ofx` 是否一致。

| 红润 | **30** | 中等，满量程改动约 58% 像素 |
| 锐化（隐藏） | 0 | 磨皮不为 0 时完全不起作用 |
| 全局锐化 | 0 | 把细节回填扩到脸外；0 时脸外逐字节不变，100 时整帧锐度可见提升 |

| 去法令纹 | 0 | SDK 侧生效，幅度较小；过大时鼻翼有涂抹感，建议 0~40 |
| 祛斑痘（隐藏） | 0 | 当前调用链上实测无效果，见上文 |
| 瘦脸（v2.1.2） | 0 | 美型三项之一（脸宽）。与磨皮/美白同开安全；**与窄脸/V脸/小脸类同开会互相打架**，所以本项目只接了三个正交维度 |
| 大眼（v2.1.2） | 0 | 美型三项之一（眼大小） |
| 下巴（v2.1.2） | 0 | 美型三项之一（下庭长度） |

美型三项的实现是**两遍渲染**：美颜（磨皮/美白/细节回填）先在原始几何上做完，
美型（几何形变）最后单独跑一遍。这样磨皮档位的手感不因开美型而改变，也不会
出现「美白糊到脸外」的鬼影。代价是美型非 0 时多一遍 SDK 渲染
（1080p +9.7 ms、4K +20.3 ms），美型全 0 时零额外开销。

另外三项：

- **磨皮模式**：人像磨皮（默认）/ 清晰磨皮 / 精细磨皮 / 朦胧磨皮。这一项决定平坦皮肤与
  轮廓各回填多少细节，与「磨皮算法」是两回事：前者管细节分配，后者管滤波类型。
- **磨皮算法**：双边滤波（最强，推荐）/ 高斯（中等）/ 弱磨皮。
  实测细节能量越低越平滑：双边 2.358 < 高斯 2.719 < 弱磨皮 3.762 < 不磨皮 4.180。
- **只磨皮肤区域**：**默认开启**。开了之后只处理检测到的皮肤区域，背景和衣服
  逐字节不动。关掉它就回到全局磨皮。

### 三个必须知道的坑

1. **磨皮和锐化互斥。** 磨皮一开，锐化的改动量实测恒为 0。想要锐化，先把磨皮拉到 0。
2. **全局滤镜已永久关闭。** 引擎的 `face_beautification` 道具里挂着一个作用于**整帧**的
   色调滤镜（`filter_name` + `filter_level`）。v1.3 早期版本照抄 OBS 插件，把它设成
   `ziran2` / `0.4`，并且「只要任意一项效果不为 0 就打开」——结果是把磨皮从 0 拉到 1，
   整帧（含背景、衣服、字幕）会被提亮 **+16/+14/+14**，灰阶曲线上是抬暗部：
   输入 25→34、128→144、229→230。这就是「磨皮会给所有画面加亮度」的成因。
   现在 `filter_name` 固定为 `origin`、`filter_level` 恒为 0（早期 Python 脚本版
   `nama_worker.py:327-328` 本来就是这么做的）。八项效果本身不受影响。
3. **美颜带人脸识别，而人脸检测对画面构图很敏感。** 插件日志里的 `faces=N`
   表示这一帧检出的人脸数。「只磨皮肤区域」依赖人脸检测：`faces=0` 时它不起作用，
   磨皮会退化成全局（但仍然不会提亮，滤镜是永久关闭的）。
   实测 43 张相机照片里只有 11 张检出人脸 —— 这些照片大多是大场景远景，人脸
   在画面里占比很小。**近景/中景人像正常检出。** 如果你在自己的素材上遇到
   `faces=0`，先看 `ofx.log`，再确认人脸在画面中的占比。

   > 历史上这里还有一个更严重的 bug：SDK 按 BGRA 读缓冲区，而引擎喂的是 RGBA，
   > AI 模型看到的是颜色错乱的脸。43 张照片里 39 张 `faces=0` 就是这个原因
   > （见下节「通道序」）。已在 SDK 边界做 R/B 交换修好。

## 性能

在 1080×1920、画面检出人脸的前提下实测（数字取自插件自己写进 `ofx.log` 的分段耗时）：

| 输入像素格式 | 转成 RGBA8 | 引擎处理 | 转回原格式 | 合计 | 等效帧率 |
|---|---|---|---|---|---|
| 8bit（Byte） | ~0.8 ms | 11–15 ms | ~0.8 ms | **~13–16 ms** | 60–75 fps |
| 32bit 浮点（Float） | ~3.5 ms | 15–16 ms | ~3.5 ms | **~18–20 ms** | 50–55 fps |

耗时的大头在人脸检测（ONNX YuNet）+ 美颜处理，像素格式转换只占 2–7 ms。
（表内毫秒数为 NamaSDK 基线期实测，v3.0.0 开源引擎版将在实机上重新标定。）
同机负载高时 SDK 那一段会涨到 20–30 ms，仍够 30fps 时间线实时预览。

**4K 全开单帧的演进**：v2.1.2 是 205 ms → v2.2.0（多线程 + SIMD + 合并转换）
降到 64.1 ms → v2.3.0（锐化中间结果改行缓存）降到 **72.9 / 78.6 ms** 区间
（两次测量口径不同，净收益 −5.7 ms / −7.3%）。4K 仍需 Render Cache 才能实时。

其他参考点：720p 全开单帧 **18.1 ms**（SDK 段 4.3 ms）；640×394 单帧 33.2 ms。

美白那一路是插件自己的 CPU 掩码（SDK 的 `color_level` 是整帧提亮，已恒关）：
1080p 约 **4.5 ms/帧**，只在「检出人脸 + 美白 > 0」时运行。这一项在 v1.4 验收时
从 **38 ms 优化到 4.5 ms**（8.4 倍）：掩码降到 1/4 分辨率、可分离羽化、缓冲复用、
提亮量预生成整数表。基准脚本：`beauty_probe\bench_whiten.py`。

四条关键设计：

- **引擎常驻 + 挂载时预热。** ONNX 会话构建 + 人脸模型（yunet.onnx）加载要花约 2.5 秒，
  这段开销被放在 `createInstance`（也就是把效果拖到片段上的那一刻），
  不再落在渲染线程的第一帧上。实测：挂载 2.5 秒，之后首帧只要 40–50 ms。
- **每帧零堆分配。** 像素缓冲、BGRA 副本、美白掩码缓冲都按引擎复用，
  1080p 每帧省掉两笔 8MB 的分配/释放。
- **转换走 AVX2。** `build.bat` 带 `/arch:AVX2`；CPU 不支持时自动退回标量分支。
- **美白不碰整帧。** 无脸时整帧逐字节不动；有脸时只提亮肤色掩码覆盖的区域。

如果回放仍然卡顿，用 **Playback → Render Cache** 缓存片段。

> **卡顿时先分清是不是本插件的锅。** 每挂一个 CPU 型 OFX 效果，帧就多一次
> 显存↔主存同步往返，而且效果在节点链上是**串行**的 —— 插件数是加法，分辨率
> 只是每项里的乘法因子。所以固定延迟压倒分辨率项之后，1080p 和 4K 会掉到
> 差不多的帧率（实测都约 16 fps）。
>
> 排查分水岭：**新建空项目 → 只挂本插件 → 看帧率**。空项目流畅就说明瓶颈在
> 项目里的其他效果，不在本插件。

## 稳定性设计

自研 CoreEngine 跑在宿主进程里。v3.0.0 起不再有闭源 DLL，但每帧处理仍可能因异常输入
或 GPU 推理失败而出错，稳定性设计遵循同样的"不让一次失败带崩宿主"原则：

- **每个 SDK 入口都包了 SEH 兜底。** 一旦抛访问违例，只让这一帧透传，
  并把引擎标记为「已停用」，本进程内不再调用 —— 否则接下来每一帧都会再崩一次。
- **初始化失败最多重试 3 次。** 每次重试要付约 2.5 秒，不能让它跟着每一帧反复发生。
- **GL 上下文用完必须还原。** 调用前保存调用线程原本的 DC/RC，调用后还原；
  切换失败时不还原（否则等于用一对旧值做无意义的 `wglMakeCurrent`）。
- **带析构函数的线程局部对象一律不用。** 缓冲用 `__declspec(thread)` 存裸指针、
  指向刻意不释放的分配，避免宿主 FreeLibrary 之后线程退出时析构函数指针悬空。
- **全 0 时走 IsIdentity。** 告诉宿主直接取源 clip 的图像，连 render 都不必调。

## 文件结构

```
ofx\
  sdk\include\       官方 OpenFX 头文件（17 个）
  examples\          官方最小示例 invert.cpp / basic.cpp
  src\nama_engine.*  引擎适配层：NamaSettings → CoreEngine 参数搬运 + 转调（经 core_glue 桥接层）
  src\ofx_plugin.cpp OpenFX 协议层：宿主对话、参数定义、日志、渲染
  build.bat          编译（手动设 INCLUDE/LIB/PATH，不依赖 vcvars64）
  install.bat        打包成 .ofx.bundle 并安装
  bundle\            打包产物
```

**注意：`.bat` 文件里不能写中文注释。** cmd.exe 按 GBK 解释批处理，
中文注释会被当成命令。源码里的中文是安全的（编译用了 `/utf-8`）。
