# DaVinci Beauty OFX —— DaVinci Resolve 美颜滤镜（v1.0.9.0）

一个给 DaVinci Resolve Studio 21.1 用的 OpenFX 滤镜，效果引擎是自研引擎 3.1.39 的
纯 CPU 美颜引擎（CoreEngine），人脸检测用 ONNX 模型，并在引擎内部**自动检测 GPU**
（仅 Windows）：把 onnxruntime.dll 换成带 GPU 支持的构建版，人脸推理
就自动走 GPU，否则自动退回 CPU。装上以后它就是一个普通滤镜：拖到片段上，拖滑块，
检视器实时刷新。v3.0.0 起彻底脱离旧版闭源商业 SDK。

这是本项目当前的主交付形态。早期做的「工作区 → 脚本」Lua 版已移出脚本菜单
（代码保留在 `C:\ProgramData\DaVinciBeauty\disabled_scripts\`），两条路线不再并存。

## v1.0.8.0 变更（2026-11-07，GPU 磨皮计时拆分 + fill 前移；推翻旧结论）

**修订位 +1**。算法、纹理格式、HLSL 一律未动，5 画幅逐字节 5/5 一致。已装机，
md5 `07c59cb6ee160b0e19961fb645c71ce6`，与 `out\` 产物一致。

1. **`mapMs` 拆成 `mapWaitMs` + `mapCopyMs`**：前者是 `Map(READ)` 调用本身（等 GPU
   同步点 + PCIe 往返），后者是拿到 `pData` 之后逐行 memcpy。两者的解法相反 ——
   等待只能靠重叠隐藏，搬运只能靠减少字节数 —— 不拆开就不知道该动哪一头。
   4K 大脸实测 3.14 / 1.09，等待占七成。
2. **ROI 外补齐前移到 Map 之前**：fill 写 ROI 之外、读回写 ROI 之内，两段严格互补。
   位置必须在 `CopySubresourceRegion` 之后，否则子区域拷贝提交变晚，反而把整帧拖长。
3. **生产日志补上两个新字段**：诊断行变成 `读回=4.23(等GPU 3.14/拷 1.09) 补齐=3.42`，
   真机日志就能直接看到拆分，不用回台架复现。

**同批修正台架两处口径错误，并推翻一个结论**：`gpu_move_bench` 的 CPU 基准多除了一次
`reps`（`cpuMs` 取的是最小值，不是累加值），1.0.7.0 记录的 `1.18 / 4.18` 实际是
`12.98 / 45.98`。修正后同一台机重测，GPU 反而快 2.4~4.7 倍。详见
`PROGRESS.md` 1.0.8.0 节 (2)(3)。

**fill 前移的收益远低于预期**：重叠率只有 8~18%。fill 是内存带宽型操作，与 GPU 经
PCIe 写 staging 的 DMA 抢同一份内存带宽，所以没有净重叠。数据与复测要求见
`PROGRESS.md` 1.0.8.0 节 (4)。

## v1.0.7.0 变更（2026-11-06，GPU 磨皮搬运瘦身；画面逐字节不变）

**修订位 +1**。只提速 + 补许可证，操作与画面都不变（18/18 基线、P2 台架 7/7）。
已装机，md5 `cb385b66d442ae5567833492d3b2ef42`。

先给 `GpuSmoothTiming` 补了分步计时（`packMs/maskMs/copyUpMs/copyDnMs/mapMs/fillMs`），
量出来才知道该改哪一行：4K 大脸时**搬运占总耗时 93~99%**，而且
`copyUp/copyDn` 只是命令提交、不占时间，真正的大头是 `map`（等 GPU + 拷回）与 `fill`。

两项改动：

1. **掩码 / 保护：一张 RGBA8 → 两张 R8_UINT**。旧实现每像素写 4 个字节
   （其中 2 个是常量）、一次一字节 store，同体积比整行 memcpy 慢 2.4 倍。改完体积降到 1/4。
   用 `R8_UINT` 不用 `R8_UNORM`：UNORM 读出来是 `value/255` 的浮点，乘回 255 不保证回到原整数。
2. **读回只拷输出矩形**：`CopyResource` 整块桶化纹理 → `CopySubresourceRegion` + `D3D11_BOX`，
   4K 大脸 15.6MB → 9.1MB。坑在于子区域拷到 staging 的 (0,0) 后，读回列偏移必须从 0 起，
   不能再减 `imgX0`（第一版照抄旧偏移，横向整体错位，台架报 maxdiff=255）。

对 HEAD 交替 5 轮（reps=11，取中位数）：1080p 大脸 3.37→2.63ms（**-22%**）、
1080p 小脸 2.43→1.88（**-23%**）、4K 小脸 6.52→5.73（**-12%**）、4K 大脸 11.62→11.29（-2.8%）、
640×394 0.62→0.57（-8%）。同台架的 CPU 列作为对照，两组差异 ≤3%，说明不是机器抖动。

**同一批数据还说明一件事**：1.0.6.0 把 CPU 路径按 ROI 裁剪之后，**GPU 路径已经比 CPU 慢
2~3 倍**（4K 大脸 11.29 vs 4.18ms，1080p 大脸 2.63 vs 1.18ms）。本算法是带宽型的，
GPU 额外付一次 PCIe 往返 + ROI 外整帧补齐，而 CPU 那侧数据本来就在内存里。
`gpu_smooth=auto` 是否还要默认启用 GPU，见 `PROGRESS.md` 第 (4) 节，待决策。

> **v1.0.8.0 更正（2026-11-07）**：上面这段的结论是反的。台架把 CPU 基准多除了一次

## v1.0.6.0 变更（2026-11-06，CPU 磨皮按 ROI 裁剪；画面逐字节不变）

**修订位 +1**（`1.0.5.0` → `1.0.6.0`）：只提速，操作与画面都不变（18/18 基线 md5 一致）。
`1.0.6.0` 已编译并装机（md5 `4b0d0b9b…`），装机件与 `out\` 产物 md5 一致；
Resolve 需重启才换上新 DLL。

`surface3RgbBand` 收了 `roi` 参数但**一次都没用过**（函数体里只有
`if (... || roi.empty()) return;` 这一处引用），整帧逐像素算，脸外像素白算。
本次真的按 roi（= 掩码包围盒 `bounds_`）外扩 halo 裁一块处理平面，只算这块，
roi 外的 dst 直接抄 src —— 等价性成立的前提是 `buildMaskInto` 只在包围盒内落笔，
所以 roi 外 mask 恒为 0，旧版在那儿走的正是「`dst = src`」那一支。

**必须记住的坑**：halo 不能只按卷积支持域算。

- 只取 `nPass·max(r1,r2+ra)+2`（1080p 约 20 像素）时，台架 8 个用例**全部差 1 个字节**。
  差异小得像浮点噪声，真因是滑动窗口每 32 像素重算一次（`kFlush`）：两次重算之间是
  「上一段的和 ± 增删」，crop 边界那圈 clamp 假值会被一路带到下一个重算点 ——
  作用半径与 r 无关，是 32/趟，且 amp 是两级级联（b2 的污染要再过一遍 amp 模糊）。
- 按 `nPass·(32 + rMax) + 2` 取（1080p = 118）后 20/20 全过；这跟
  `P2_GPU磨皮施工图.md` 第 7.1 节写的 `passes×32 + passes×(r2+ra) + 2` 是同一个式子，
  只是那次写在 GPU 侧，这次轮到 CPU 真的用上。
- 起点还要 `alignDown32`，让重算点落在同一批全局坐标上，否则浮点相位不同会差出灰阶。

**代价与收益（台架 `03_测试夹具/cpu_roi_test.cpp`，8 线程，每项 5 次中位）**：

| 场景 | 整帧 | 裁剪 | 倍数 |
|---|---|---|---|
| 1080p，roi 22%（典型人脸） | 21.8~44.7ms | 14.2~29.8ms | 1.50~1.54× |
| 1080p，roi 5~6% | 15.6~17.0ms | 3.3~5.4ms | 3.2~4.8× |
| 4K，roi 5~6% | 63.1~89.6ms | 15.0~15.3ms | 4.2~5.9× |
| 4K，roi 18~22% | 64.4~72.6ms | 30.0~39.3ms | 1.85~2.15× |
| 4K，roi 74%（大脸） | 88.5ms | 86.3ms | 1.03×（无收益，也无回退） |
| 640×394（小画幅） | — | — | 0.96~1.44×（halo 占比过大） |

**`P2 施工图` 里「估算 4~6×」只在脸小时成立**：典型人脸是 1.5×，小脸/4K 才到 4~6×。
而且这一条只在 **CPU 回落路径**有效（`gpu_smooth=auto` 时生产走 GPU）。
更激进的裁剪（b1/b2 用 118、amp 用 236 两块 crop）能再抬一点，但复杂度不成比例，
本次没做。

## v1.0.5.0 变更（2026-11-06，BUG4 多实例串台：per-slot 状态 + 互斥）

`CoreEngine` 的磨皮中间态（掩码、对齐帧、EMA 历史）原先是一份**共享成员**，
两个实例同时渲染会互相换走，表现为「V1/V2 都挂美颜时合成塌陷成固定一层」。
本次改成 per-slot 状态，并给整个 `process()` 作用域加一把
`std::recursive_mutex`（`slotStateMx()`），`releaseSlot()`/`release()` 先拿同一把锁
再 `erase`/`clear`，顺带消掉 `slotOf()` 返回引用后表被清空的悬垂。

同一批修掉的还有三处：`lastFaces()/lastFaceScore()/lastErr()` 的快照改
`thread_local`（原先会被另一实例覆盖，`c_str()` 还可能悬垂）、
`g_beautyDiagFrameSubst` 改 `thread_local`、
`gpuBeautyShutdown`/`gpuSmoothShutdown` 原是**全工程零调用点**的死代码，现挂到
`onUnload`，且 `createDevice` 半失败（设备建好、着色器编译失败）时也会拆干净。

代价要说清楚：两个实例的 `process()` 现在**串行**。彻底并行需要把状态改成按 slot
传参，属引擎层重写，本次没做。并发证据：同源链接的
`03_测试夹具/bug4_concurrency_test.cpp`，去掉锁的对照组第 0 帧就串台，
加锁版 20/20 帧逐字节一致。

```cpp
const int growP = passes * 32 + passes * (r2 + ra) + 2;
//               ↑ 新增项        ↑ 模糊传播        ↑ 双线性
```

污染再一块一块往里传染、共传 `passes` 次 → 污染半径恰好 `32 × passes`。
实测差异在内缩 **96 像素**处归零，与 `32 × 3` 完全吻合。

## 版本号规则（2026-11-06 起，四段式）

```
1 . 0 . 0 . 0
│   │   │   └── 构建位  改注释/文档/日志/打包，不影响行为
│   │   └────── 修订位  修 bug / 调默认值 / 提速，没加东西

```

**口诀：用户能看出来吗？** 看不出→构建位｜变好了但不坏了→修订位｜多了个东西→功能位｜
以前的设置全乱了→主版位。跨档取最高，低位归零。

**低位不进位**：修订位可以从 9 涨到 10、20，不必攒够就顶到功能位。
旧的三段式规则里「重要更新→中间位+1 且最右归零」把中间位触发得太频繁，
一年多就从 1.0 顶到 3.3.0，所以本次一次性重置为 `1.0.0.0`。

## v3.2.0 变更（2026-11-05，ROI 优先的 GPU 传输管道）

新增 `src/gpu_beauty.h/.cpp`：D3D11 device 懒创建（独显优先）、**只按人脸 ROI
分配纹理**、上传/下载均按行抽取，`Map(READ)` 单次自然阻塞（不插 fence）。

关键实测（`_p1bench/gpu_pipe_test.cpp`，RGBA8 口径）：

| 场景 | ROI | 往返耗时 | 一致性 |
|---|---|---|---|
| 4K 人脸 | 1280×1440 | **3.60ms** | 逐字节一致 |
| 4K 全帧 | 3840×2160 | 15.34ms | 逐字节一致 |
| 1080p 人脸 | 960×800 | **0.94ms** | 逐字节一致 |

真实宿主 DLL 内（`NamaSelfTest` 62 帧）：ROI 466×704，**0.74ms/帧**，60 帧
不一致字节数 = 0；开关前后输出 md5 相同，画面逐字节不变。

三个必须记住的坑（详见 PROGRESS）：

1. **引擎帧缓冲是 RGBA8，不是 float32** —— 按 f32 读会 4 倍越界崩溃。
2. **显式 `QUERY_EVENT`+`Flush` 固定 11~15ms**（Optimus 同步代价），管道里禁止使用。
3. **DYNAMIC 纹理不能直接当 SRV** —— 驱动会影子拷贝，1ms 变 15ms。

本版只打通管道，磨皮 21 趟的移植是 P2。

## v3.0.8 变更（2026-10-31，工程验收 + 性能优化，画面逐字节不变）

只改「能不能稳定构建 / 装机判据 / 每帧内存搬运 / 测试覆盖 / 死代码」。

**（1）构建链路：.bat → PowerShell。** 旧 `build.bat` 把 `..\02_引擎资产\onnxruntime\include`

cl 直接报 `cannot open include file: onnxruntime_c_api.h`（本次验收第一次构建就复现）。
`%~dp0` 这类动态展开没事，**出问题的永远是批处理里的中文字面量**。
现在 `build.bat` 只是 `build.ps1` 的薄壳：vswhere 探测 VS → 取最新 MSVC 与 Windows SDK →

`net session` 判权限：受限的管理员令牌（UAC 未提升、但目标目录 ACL 已放行）会被误判成

现在只在 `mkdir "%TARGET%"` 失败时报错 —— 创建目录才是唯一诚实的判据。

**（3）8bit 直通路径：省掉两次全帧拷贝。** 宿主给 8bit、行无填充、输入输出 bounds 一致时

两次 8.3MB/帧的搬运纯属多余。现在引擎直接读源图、写目标图（`src`/`dst` 是宿主给的
两张不同图像，引擎对 `src` 只读 —— 见 `beauty_core.h` 的 `process()` 契约）。
1080p A/B 交替 5 轮取最小值：**24.5 → 20.5 ms/帧**。float、bounds 不一致、有行填充的
路径保持原样；float 输出的逐像素统计（改动≥3 的像素 8287、残留哨兵 203）与旧版一致。

**（4）测试覆盖：14 个滑块逐个独奏。** `baseline.py` 只覆盖 6 个参数，「立体 / 亮眼 /

| top-down（v3.0.3 及以前） | **0.2519** | 0 |
| bottom-up（v3.0.4） | **0.9333** | **1** |

**OFX 规范规定 `kOfxImagePropData` 指向图像左下角**，Resolve 严格照做（第 0 行是画面最下面一行）；
而 PIL/numpy 与所有离线夹具都按 top-down 存帧 → 「离线 0.92 通过、真机 0.25 全灭」。

实现：`letterboxRgb()` 本就要缩放重采样，读行直接换成 `sh-1-y`（零成本，不整帧翻转）；
检测出的框/关键点是视觉坐标，再映射回缓冲行号（`f.y = h - vy - f.h`、`kps.y = h - vy`），
掩码/磨皮/美白/几何变形全按缓冲行号落笔，下游一行不改。引擎默认 `imgBottomUp_ = true`。

配套：`mock_host.py` 新增 `_to_bottom_up()`（夹具帧序与真机一致，此前夹具替插件掩盖了方向 bug）；
`NamaSelfTest` 恢复 `NAMA_ST_*` 钩子并强制关异步（此前 8 个基线用例实际只覆盖 4 种参数、且不可复现）；

## v2.0.1 变更（2026-10-26，Resolve 内实测后修复）

来自装机后逐项试用的四条反馈：三处真缺陷，一处命名与行为相反。

### 1. 日志从来没有写出来过（修）

`ofxLog()` 用 `CreateDirectoryA` 只建**一级**目录。装机后 `C:\ProgramData\DaVinciBeauty`
本身不存在，于是 `...\logs` 建不出来、`fopen` 失败、每条日志被静默丢弃 ——
插件在 Resolve 里跑多久都不会产生 ofx.log，这段时间「出错就看日志」的排查其实都是空的。
旧代码还有 `static bool dirOk` 无条件置位，第一次失败就永久放弃重试。

现在按分隔符逐段创建，只有确认目录真的存在后才缓存。
实测：删掉整个 `C:\ProgramData\DaVinciBeauty` 后跑一次，日志自动重建。

### 2. 磨皮四档实际是「磨皮 + 50 档锐化」（修，本次最重要）

用户原话「只有第一个选项达到快速磨皮且保留质感，其余只有锐化的效果」，
在代码里能一字不差地找到原因。

`texModeNeedsBaseline` 给模式 1/2/3 一个「基准回填」，基准取「锐化 50」。
而 faceAmt 同时驱动两件事：细频带 alpha，以及

    midGain = (faceAmt/100) * kMidGain = 0.5 * 3.30 = 1.65

按 `kMidGain` 自己的标定注释，锐化 50 就是把 3~7px 中频带推到原图的 **149.8%** ——
那正是「锐化」的定义。模式 0 不带基准回填、根本不走这条路径，才是纯 SDK 磨皮。

修法：基准回填**只给细频带**，中频增益只在用户显式动了「锐化」或「清晰」时才给。

实测（640×394 人像帧，磨皮 50，相对原图的高频能量）：

| 选项 | 细频·平坦区 | 细频·边缘区 | 中频 3~7px |
|---|---|---|---|
| 0 人像磨皮 | 92.3% | 100.2% | 98.8% |
| 1 清晰磨皮 | 94.3% | 107.1% | 101.0% |
| 2 精细磨皮 | 96.8% | 104.2% | 100.1% |
| 3 轻磨皮 | 96.7% | 101.5% | 99.2% |
| 对照：真正的锐化 50 | 105.6% | 106.5% | 108.2% |
| 对照：真正的锐化 100 | 116.3% | 111.9% | 116.3% |

四档全部低于 100%（都是磨皮），锐化 50 才把它推到 100% 以上。

### 3. 「朦胧磨皮」名不副实（改名）

`kTexModes[3] = {140,0,0}` 的语义是「按面板档位的 55% 回填细频」，是**正回填**。
本引擎没有负回填（hf 取自原图，减它会把边缘挖穿），所以它做不到「比纯磨皮更糊」。
实测它是四档里细节留得最多的一档，故改名 **「轻磨皮（细节保留最多）」**。
四档文案同步按实测排序：人像（SDK 原始质感）/ 清晰（轮廓最立体）/
精细（轮廓小幅增强）/ 轻磨皮（细节保留最多）。

### 4. 输入像素编码自检（新增）

引擎把输入一律当非线性编码像素处理（`f32_to_u8_row` 是纯 `v*255`）。这在下述配置下
正确：色彩科学 DaVinci YRGB（非 Color Managed）+ 时间线 Rec.709 (Scene) ——
送入的就是 Rec.709 编码值。

但换到 Color Managed / ACES 项目时宿主可能改送 scene-linear，那时 18% 灰会被映射成
46/255 而不是 105/255：画面压暗、人脸漏检、美白比例失真，**且不报错**。

现在每个实例在首帧采一次亮度分布写进日志：

    inputProbe 中位=123/255 黑1%=0 亮99%=231（非线性编码，正常范围）

中位 < 55 就记 WARN（已排除纯黑遮幅，否则黑边会让中位恒为 0）。
**不做自动补偿** —— 补偿需要确切的传递函数，猜错比不补偿更糟。

### 什么时候要重启 Resolve

Resolve 把扫描结果缓存在
`%APPDATA%\Blackmagic Design\DaVinci Resolve\Support\OFXPluginCacheV2.xml`，
缓存以 `mtime + size` 判断是否失效：

- **重新编译过插件** → 二进制指纹变了 → **必须重启 Resolve** 才会重新扫描。
- **只是重启 Resolve、没改过插件** → 走缓存，不需要额外操作。

想确认 Resolve 认没认，直接看那个 xml 里有没有 `com.nama.davinci.beauty`，
并核对 `mtime` / `size` 与磁盘上的 `DaVinciBeauty.ofx` 是否一致。

| 参数 | 默认 | 实测效果强度 |
|---|---|---|
| 磨皮 | **50** | 最强项。v2.0 是线性曲线：50~62 为轻磨皮，70~90 较明显；1.x 的 20 约等于本版 70~80。（62 是 v2.0.3 对标同类产品默认档的 GT 实测档位，v2.2.3 起按用户观感决策改回 50） |
| 清晰 | 0 | 很强，满量程改动约 89% 像素 |
| 美白 | **30** | 只提亮肤色（语义掩码），满量程皮肤区约 +10（v1.51 为 +25，见上文标定说明） |
| 红润 | **30** | 中等，满量程改动约 58% 像素 |
| 锐化（隐藏） | 0 | 磨皮不为 0 时完全不起作用 |
| 全局锐化 | 0 | 把细节回填扩到脸外；0 时脸外逐字节不变，100 时整帧锐度可见提升 |

| 亮眼 | 0 | 很弱，满量程只改动约 0.65% 像素，要放大才看得出 |
| 去黑眼圈 | 0 | 很弱，满量程只改动约 0.93% 像素 |
| 去法令纹 | 0 | SDK 侧生效，幅度较小；过大时鼻翼有涂抹感，建议 0~40 |
| 祛斑痘（隐藏） | 0 | 当前调用链上实测无效果，见上文 |
| 瘦脸（v2.1.2） | 0 | 美型三项之一（脸宽）。与磨皮/美白同开安全；**与窄脸/V脸/小脸类同开会互相打架**，所以本项目只接了三个正交维度 |
| 大眼（v2.1.2） | 0 | 美型三项之一（眼大小） |
| 下巴（v2.1.2） | 0 | 美型三项之一（下庭长度） |

美型三项的实现是**两遍渲染**：美颜（磨皮/美白/细节回填）先在原始几何上做完，
美型（几何形变）最后单独跑一遍。这样磨皮档位的手感不因开美型而改变，也不会
出现「美白糊到脸外」的鬼影。代价是美型非 0 时多一遍 SDK 渲染
（1080p +9.7 ms、4K +20.3 ms），美型全 0 时零额外开销。

另外三项：

- **磨皮模式**：人像磨皮（默认）/ 清晰磨皮 / 精细磨皮 / 朦胧磨皮。这一项决定平坦皮肤与
  轮廓各回填多少细节，与「磨皮算法」是两回事：前者管细节分配，后者管滤波类型。
- **磨皮算法**：双边滤波（最强，推荐）/ 高斯（中等）/ 弱磨皮。
  实测细节能量越低越平滑：双边 2.358 < 高斯 2.719 < 弱磨皮 3.762 < 不磨皮 4.180。
- **只磨皮肤区域**：**默认开启**。开了之后只处理检测到的皮肤区域，背景和衣服
  逐字节不动。关掉它就回到全局磨皮。

### 三个必须知道的坑

1. **磨皮和锐化互斥。** 磨皮一开，锐化的改动量实测恒为 0。想要锐化，先把磨皮拉到 0。
2. **全局滤镜已永久关闭。** 引擎的 `face_beautification` 道具里挂着一个作用于**整帧**的
   色调滤镜（`filter_name` + `filter_level`）。v1.3 早期版本照抄上一代插件，把它设成
   `ziran2` / `0.4`，并且「只要任意一项效果不为 0 就打开」——结果是把磨皮从 0 拉到 1，
   整帧（含背景、衣服、字幕）会被提亮 **+16/+14/+14**，灰阶曲线上是抬暗部：
   输入 25→34、128→144、229→230。这就是「磨皮会给所有画面加亮度」的成因。
   现在 `filter_name` 固定为 `origin`、`filter_level` 恒为 0（早期 Python 脚本版
   `nama_worker.py:327-328` 本来就是这么做的）。八项效果本身不受影响。
3. **美颜带人脸识别，而人脸检测对画面构图很敏感。** 插件日志里的 `faces=N`
   表示这一帧检出的人脸数。「只磨皮肤区域」依赖人脸检测：`faces=0` 时它不起作用，
   磨皮会退化成全局（但仍然不会提亮，滤镜是永久关闭的）。
   实测 43 张相机照片里只有 11 张检出人脸 —— 这些照片大多是大场景远景，人脸
   在画面里占比很小。**近景/中景人像正常检出。** 如果你在自己的素材上遇到
   `faces=0`，先看 `ofx.log`，再确认人脸在画面中的占比。

   > 历史上这里还有一个更严重的 bug：SDK 按 BGRA 读缓冲区，而引擎喂的是 RGBA，
   > AI 模型看到的是颜色错乱的脸。43 张照片里 39 张 `faces=0` 就是这个原因
   > （见下节「通道序」）。已在 SDK 边界做 R/B 交换修好。

## 性能

在 1080×1920、画面检出人脸的前提下实测（数字取自插件自己写进 `ofx.log` 的分段耗时）：

| 输入像素格式 | 转成 RGBA8 | 引擎处理 | 转回原格式 | 合计 | 等效帧率 |
|---|---|---|---|---|---|
| 8bit（Byte） | ~0.8 ms | 11–15 ms | ~0.8 ms | **~13–16 ms** | 60–75 fps |
| 32bit 浮点（Float） | ~3.5 ms | 15–16 ms | ~3.5 ms | **~18–20 ms** | 50–55 fps |

耗时的大头在人脸检测（ONNX 模型推理）+ 美颜处理，像素格式转换只占 2–7 ms。
（表内毫秒数为旧引擎基线期实测，v3.0.0 开源引擎版将在实机上重新标定。）
同机负载高时 SDK 那一段会涨到 20–30 ms，仍够 30fps 时间线实时预览。

**4K 全开单帧的演进**：v2.1.2 是 205 ms → v2.2.0（多线程 + SIMD + 合并转换）
降到 64.1 ms → v2.3.0（锐化中间结果改行缓存）降到 **72.9 / 78.6 ms** 区间
（两次测量口径不同，净收益 −5.7 ms / −7.3%）。4K 仍需 Render Cache 才能实时。

其他参考点：720p 全开单帧 **18.1 ms**（SDK 段 4.3 ms）；640×394 单帧 33.2 ms。

美白那一路是插件自己的 CPU 掩码（SDK 的 `color_level` 是整帧提亮，已恒关）：
1080p 约 **4.5 ms/帧**，只在「检出人脸 + 美白 > 0」时运行。这一项在 v1.4 验收时
从 **38 ms 优化到 4.5 ms**（8.4 倍）：掩码降到 1/4 分辨率、可分离羽化、缓冲复用、
提亮量预生成整数表。基准脚本：`03_测试夹具\bench_whiten.py`。

四条关键设计：

- **引擎常驻 + 挂载时预热。** ONNX 会话构建 + 人脸模型（yunet.onnx）加载要花约 2.5 秒，
  这段开销被放在 `createInstance`（也就是把效果拖到片段上的那一刻），
  不再落在渲染线程的第一帧上。实测：挂载 2.5 秒，之后首帧只要 40–50 ms。
- **每帧零堆分配。** 像素缓冲、BGRA 副本、美白掩码缓冲都按引擎复用，
  1080p 每帧省掉两笔 8MB 的分配/释放。
- **转换走 AVX2。** `build.bat` 带 `/arch:AVX2`；CPU 不支持时自动退回标量分支。
- **美白不碰整帧。** 无脸时整帧逐字节不动；有脸时只提亮肤色掩码覆盖的区域。

如果回放仍然卡顿，用 **Playback → Render Cache** 缓存片段。

> **卡顿时先分清是不是本插件的锅。** 每挂一个 CPU 型 OFX 效果，帧就多一次
> 显存↔主存同步往返，而且效果在节点链上是**串行**的 —— 插件数是加法，分辨率
> 只是每项里的乘法因子。所以固定延迟压倒分辨率项之后，1080p 和 4K 会掉到
> 差不多的帧率（实测都约 16 fps）。
>
> 排查分水岭：**新建空项目 → 只挂本插件 → 看帧率**。空项目流畅就说明瓶颈在
> 项目里的其他效果，不在本插件。

## 稳定性设计

自研 CoreEngine 跑在宿主进程里。v3.0.0 起不再有闭源 DLL，但每帧处理仍可能因异常输入
或 GPU 推理失败而出错，稳定性设计遵循同样的"不让一次失败带崩宿主"原则：

- **每个 SDK 入口都包了 SEH 兜底。** 一旦抛访问违例，只让这一帧透传，
  并把引擎标记为「已停用」，本进程内不再调用 —— 否则接下来每一帧都会再崩一次。
- **初始化失败最多重试 3 次。** 每次重试要付约 2.5 秒，不能让它跟着每一帧反复发生。
- **GL 上下文用完必须还原。** 调用前保存调用线程原本的 DC/RC，调用后还原；
  切换失败时不还原（否则等于用一对旧值做无意义的 `wglMakeCurrent`）。
- **带析构函数的线程局部对象一律不用。** 缓冲用 `__declspec(thread)` 存裸指针、
  指向刻意不释放的分配，避免宿主 FreeLibrary 之后线程退出时析构函数指针悬空。
- **全 0 时走 IsIdentity。** 告诉宿主直接取源 clip 的图像，连 render 都不必调。
